1、MiniCode 的整体系统架构

MiniCode 是一个面向代码理解、修改和任务执行的 Coding Agent 原型系统。基础的agent分为四个大部分：感知、规划、行动、反馈

第一个部分就是感知部分，涉及到一些输入处理，比如文档怎么拆，怎么使用RAG等等，在这个项目中第一层是 User Interface / Task Input 层，负责接收用户请求。

第二个部分就是规划，本质就是一个react循环，第二层是 Planner / Controller 层，它负责理解任务、拆解步骤、维护状态、选择工具、判断是否继续执行，以及决定最终什么时候结束任务。

第三个部分就是行动，第三层是 Tool Use 层，例如读取文件、写文件、搜索文件、运行 shell 命令、执行测试、查看 git diff、静态分析等。

第四层是 Skill 层，Skill 会把多个工具调用和提示词策略组织成可复用流程。第五层是 Memory 层，用于保存跨任务、跨会话可以复用的信息，包括用户偏好、项目经验、错误修复经验、常用命令、项目结构摘要等。

第四个部分就是反馈，第六层是 Context Management 层，因为 Coding Agent 经常面对大量文件、日志、工具返回结果和历史对话，如果全部塞进 prompt，会导致 token 成本过高、上下文污染、模型注意力分散。所以我设计了摘要、占位、外置化、按需检索等机制来控制上下文。

2、Query Loop （查询循环）+ Tool Use 的完整流程

本质是让 Agent 不断在“思考下一步动作”和“调用工具获取环境反馈”之间迭代，直到任务完成或达到终止条件，Tool Use 给 Agent 提供与外部环境交互的能力。

3、Tool Calling 在系统里怎么实现

MiniCode 中的 Tool Calling 我设计成“模型决策 + 结构化 schema + 系统执行器”的形式。模型只负责选择工具和生成参数，真正的执行由后端工具层完成。这样可以保证工具调用可控、可校验、可审计。

每个工具都有一个 schema，主要包括：

工具名，例如 read_file。

工具描述，说明这个工具适合什么场景。

参数定义，规定参数字段、类型、是否必填。

权限级别，区分只读工具、写入工具、命令执行工具、危险工具。

路径边界，限制工具只能访问项目工作区内的文件。

返回格式，规定 observation 如何返回给模型。

模型如何知道什么时候调用工具？

主要依赖三部分信息：

第一，系统提示词会告诉模型：当信息不足时不能编造，必须调用工具获取事实。例如不知道文件内容，就调用 read_file；不知道项目结构，就调用 list_dir；需要定位函数，就调用 search_code；修改后要验证，就调用 run_command。

第二，工具 schema 会告诉模型每个工具的功能边界。比如 read_file 只能读文件，不能搜索；search_code 适合定位关键词；edit_file 适合做局部修改。

第三，Agent 当前状态会引导工具选择。比如当前阶段是“定位问题”，就更可能调用搜索和读取工具；当前阶段是“验证修复”，就更可能调用测试命令；当前阶段是“生成总结”，就不需要继续调用工具。

4、工具调用参数错误时 Agent 如何处理

如果模型调用工具时参数错误，MiniCode 不会直接终止，而是把错误作为 observation 返回给 Agent，让 Agent 进行自我修正。整体上我设计了三类机制：参数校验、错误分类、retry / reflection / fallback。

首先是 参数校验。工具执行前，系统会检查参数是否符合 schema。比如必填字段是否缺失，字段类型是否正确，路径是否存在，路径是否越界，命令是否安全，是否有写权限。如果校验不通过，工具不会执行，而是返回结构化错误。

其次是 错误分类。不同错误对应不同处理策略。

如果是路径不存在，一般是可恢复错误。Agent 会调用 list_dir、search_code 或重新推断路径。

如果是参数格式错误，比如 JSON 字段不对，Agent 会根据 schema 重新生成参数。

如果是命令执行失败，比如测试失败，Agent 会读取 stderr，判断是环境问题、依赖问题，还是代码逻辑问题。

如果是权限不足，系统不会自动绕过，而是停止危险操作，要求用户授权或换安全方案。

如果是危险命令，例如删除大量文件、访问系统目录，系统直接拦截，不让模型自行 retry。

然后是 retry 机制。对于可恢复错误，可以允许有限次数 retry，例如最多 2 到 3 次。每次 retry 不能简单重复原工具调用，而必须根据错误信息修改动作。

再是 reflection 机制。当连续失败或测试结果与预期不一致时，Agent 会进入反思阶段。反思不是泛泛地说“我错了”，而是结构化分析：

当前目标是什么？

刚才执行了什么？

失败类型是什么？

失败是工具参数问题、环境问题、代码理解问题，还是计划问题？

下一步应该修正参数、换工具、回退修改，还是请求用户确认？

最后是 fallback 机制。如果某个工具不可用，Agent 会选择替代路径。

例如：

ripgrep 不可用，可以 fallback 到 Python 文件遍历搜索。

测试命令失败，可以先查看项目配置文件，例如 pyproject.toml、requirements.txt、package.json。

不能直接修改文件时，可以输出 patch 建议，让用户手动确认。

无法访问完整文件时，可以基于已读取片段给出局部分析，并说明不确定性。

5、Tool、Skill、高层 Skill 的区别，以及为什么不直接让模型从所有工具里选

在 MiniCode 里，我把能力分成三层：Tool、Skill、高层 Skill。它们的区别主要在抽象层级、复用粒度和执行复杂度。

Tool 是最底层的原子能力。

Tool 通常只完成一个非常具体的动作，例如：

读取文件：read_file

写入文件：write_file

搜索代码：search_code

列目录：list_dir

运行命令：run_command

查看 diff：git_diff

检索记忆：memory_retrieve

Tool 的特点是粒度小、功能明确、输入输出结构化、容易做权限控制。它不理解完整任务，只执行一个动作。

Skill 是由多个 Tool 和策略组合成的中层能力。

Skill 面向一类常见任务流程，比如：

定位 bug

生成单元测试

解释项目结构

重构函数

根据报错修复代码

分析依赖问题

例如“定位 bug”这个 Skill 可能包含以下步骤：

读取错误日志。

从日志中提取文件名、函数名、异常类型。

搜索相关代码。

读取关键文件。

分析调用链。

给出可能原因。

必要时运行最小复现测试。

它不是一个单一工具，而是一套可复用的流程模板。

高层 Skill 是更复杂的任务级能力。

高层 Skill 可以调用多个普通 Skill，适合项目级任务。例如：

“自动修复一个 issue”

“为一个模块补充测试”

“迁移项目依赖版本”

“进行代码质量审查”

以“自动修复 bug”为例，它可能调用：

项目结构分析 Skill

错误日志分析 Skill

代码定位 Skill

代码修改 Skill

测试验证 Skill

最终报告 Skill

所以三者关系可以理解为：

1
2
3

Tool：最小动作，例如读文件、跑命令
Skill：多步流程，例如定位 bug、生成测试
高层 Skill：任务级工作流，例如自动修复 issue

为什么不直接让模型从所有工具里选？

主要有五个原因。

第一，工具太多会增加选择噪声。 如果系统里有几十个甚至上百个工具，全部暴露给模型，模型会更容易选错工具，或者在功能相似的工具之间混淆。比如 search_file、search_code、grep_symbol、semantic_search 都和搜索有关，模型不一定每次都能选最合适的。

第二，工具列表太长会占用大量 token。 每个工具都要提供 name、description、parameters、example。如果全部放进 prompt，会显著增加上下文成本，尤其在 Coding Agent 长任务中，这会挤占代码内容、错误日志、计划状态的空间。

第三，原子工具缺乏任务流程知识。 模型直接从工具中选，只解决“下一步调用什么”的问题，但复杂任务需要稳定流程。例如修 bug 不是简单读文件和改文件，而是需要先定位、再理解、再修改、再测试、再回滚或总结。Skill 可以把这些流程沉淀下来，减少每次都重新规划的成本。

第四，Skill 更容易沉淀经验。 如果某类任务经常出现，比如 Python 项目测试失败、依赖冲突、路径导入错误，就可以把成功经验固化成 Skill。下次遇到类似任务时，Agent 可以直接复用，而不是每次从零推理。

第五，安全控制更清晰。 Tool 层可以控制原子权限，Skill 层可以控制流程边界。例如某个 Skill 允许读文件和运行测试，但不允许删除文件；某个高层 Skill 可以生成 patch，但必须等待用户确认后才能写入。这样比直接给模型开放所有工具更安全。

6、Skill 路由中的“两阶段召回与精排”具体怎么做？

当系统里有很多 Skill 时，Agent 怎么从一堆 Skill 中找到最适合当前任务的 Skill。

第一阶段是粗召回，目标是快速从大量 Skill 中筛出少量候选；第二阶段是精排，目标是结合任务上下文、Skill 适用边界、输入输出要求和历史表现，对候选 Skill 重新排序，最终选出最合适的 Skill 或 Skill 组合。

第一阶段：粗召回

第一阶段不追求绝对准确，追求 快、便宜、召回率高。它的目标不是直接决定用哪个 Skill，而是先从大量 Skill 中挑出 top-k 个候选，比如从 500 个 Skill 中召回 10 个。

第一阶段可以混合使用三种方法：关键词规则、embedding 语义召回、元信息过滤。

第一种是 关键词 / 规则召回。

第二种是 embedding 语义召回。每个 Skill 都会提前构建一段可检索文本，例如：

7、Skill 会“自进化增长”，如何避免检索噪声？如何判断一个 Skill 是否应该被复用？

Skill 自进化增长的风险在于，Skill 数量越多，功能重叠、描述相似、质量不稳定的问题越明显。如果没有治理机制，路由阶段会召回很多半相关 Skill，导致模型选错、token 成本上升、执行路径不稳定。所以我会从 Skill 写入、索引、检索、复用判断和淘汰合并五个层面控制噪声。

第一，Skill 写入前要有准入标准、第二，Skill 入库时要做去重和合并、第三，Skill 检索时要做分层索引，第四，Skill 要有质量评分和生命周期、第五，如何判断一个 Skill 是否应该被复用？

8、两个 Skill 功能重叠时，系统怎么决定用哪个？

当两个 Skill 功能重叠时，我不会只根据名字选择，而是根据任务目标、操作粒度、输入范围、输出形式、风险等级和历史效果做 disambiguation。如果仍然无法确定，就优先选择更小粒度、更低风险的 Skill，或者向用户确认。

10、权限安全审查：Agent 想执行 rm -rf、访问隐私文件、修改系统配置，怎么拦截？

不会让模型直接拥有系统权限。所有危险操作都必须经过工具层的权限审查。模型只能提出 tool call，真正执行前由系统做参数校验、路径检查、命令风险识别、权限分级和必要的人类确认。对于 rm -rf、访问隐私文件、修改系统配置这类高风险操作，默认直接拦截或进入人工确认，不允许 Agent 自行执行。

权限审查可以分成四层，第一层：工具级权限控制。第二层：参数级校验。第三层：策略级审查。第四层：结果级审查。

11、记忆具体分为哪几类？程序性经验、情景记忆、用户画像分别存什么？

这个问题可以这样回答：在 MiniCode 里，我没有把所有历史信息都放进一个统一的 memory 池，而是按照用途把记忆分成几类。最核心的是程序性记忆、情景记忆、语义记忆和用户画像记忆。这样做的原因是，不同类型的记忆在写入标准、检索方式、更新频率和安全边界上都不一样。如果全部混在一起，后续检索时很容易召回噪声，甚至把一次性历史任务误当成长期偏好。

程序性记忆主要存的是“怎么做某类任务”的经验，也就是可复用的操作流程。例如，处理 Python pytest 报错时，应该先读取 traceback，再定位失败测试文件，再搜索被测函数，再读取源码和测试代码，最后做最小修改并运行目标测试。这个记忆不是关于某一次具体任务的，而是关于一类任务的通用流程。它更接近 Skill 或操作策略，后续遇到类似任务时可以直接复用。

情景记忆存的是某一次具体任务的上下文和执行轨迹。例如，某次用户让我修复一个登录模块的 bug，当时项目结构是什么、报错日志是什么、我读了哪些文件、做了哪些修改、测试结果如何、最后有没有成功。这类记忆有明确的时间、项目、任务背景，适合在用户回到同一个项目或追问“上次那个问题继续处理”时使用。它不一定能泛化到所有项目，但对当前项目的连续任务很有价值。

语义记忆存的是相对稳定的事实性知识，尤其是项目级事实。例如，这个项目使用 FastAPI，测试框架是 pytest，入口文件在 src/main.py，配置文件是 pyproject.toml，模型推理模块在 inference/ 目录。这类信息不是用户偏好，也不是一次执行步骤，而是对项目结构和技术栈的抽象总结。它可以帮助 Agent 在后续任务中更快建立上下文，不必每次都重新扫描项目。

用户画像记忆存的是用户长期稳定的偏好和约束。例如，用户希望回答简洁一些，用户偏好 Python，用户做实验时优先使用 DeepSeek API，不希望随便引入无关实验，或者在某个项目中更关注可复现性而不是花哨优化。这类记忆不能随便写入，必须判断它是不是长期有效、是不是用户明确表达的偏好、是不是会影响后续交互。它和项目记忆要分开，因为“用户喜欢简洁回答”是跨项目偏好，而“这个项目使用 PyTorch”只是某个项目的事实。

每条记忆都会带上类型、来源、时间、项目 ID、适用范围、置信度、是否可更新等元数据。这样后续检索时可以按任务类型和上下文筛选，而不是简单做全库向量搜索。

12、“执行-反思-提炼-分类存储-索引更新-按需复用”中，每一步由谁完成？LLM 还是规则/代码？

“执行”阶段主要由 Agent Loop 和工具系统完成。模型决定下一步调用什么工具，后端执行器负责真实执行工具，比如读文件、搜索代码、运行测试、修改文件。每一步会产生结构化日志，包括用户目标、工具调用、参数、返回结果、错误信息、修改 diff 和测试结果。这一步的关键不是记忆写入，而是把完整轨迹记录下来，作为后续反思和提炼的原材料。

“反思”阶段主要由 LLM 完成，但触发条件由规则控制。比如工具连续失败、测试失败、任务完成、用户显式确认结果有效，都会触发 reflection。LLM 在反思阶段要回答几个问题：这次任务目标是什么，采用了什么路径，哪些步骤有效，哪些步骤失败，失败原因是什么，有没有形成可复用经验。这里需要模型的语义理解能力，因为它要从工具日志和代码上下文中抽取经验。

“提炼”阶段也主要由 LLM 完成。它会把原始执行轨迹压缩成更高层的经验。例如，原始日志可能包含十几轮工具调用，但最终提炼出的经验是：“当 pytest 出现 ModuleNotFoundError: No module named src 时，优先检查项目根目录、PYTHONPATH、pytest 配置和包初始化文件，而不是直接修改业务代码。”这个过程需要抽象能力，所以适合交给 LLM。

“分类存储”不能完全交给 LLM。LLM 可以建议这条记忆属于程序性记忆、情景记忆、项目语义记忆还是用户画像记忆，但最终系统要根据规则校验。比如包含“用户以后都希望……”这类长期偏好，才可能进入用户画像；包含具体项目路径和配置，应该进入项目语义记忆；包含一次任务轨迹，应该进入情景记忆；包含通用操作流程，才进入程序性记忆。系统还要检查是否包含敏感信息、是否重复、是否置信度足够。

“索引更新”主要由代码完成。比如把记忆写入数据库，生成 embedding，更新向量索引，写入 keyword index，更新 metadata filter。LLM 不应该直接操作索引。它最多生成记忆内容和标签，真正的存储、去重、版本管理、过期策略和权限控制都应该由系统代码完成。

“按需复用”是 LLM 和规则共同完成。规则先根据当前任务类型、项目 ID、用户 ID、时间范围、memory 类型做过滤，再用 embedding 或关键词召回候选记忆。LLM 再对候选记忆做判断，决定哪些真的有用，哪些只是相似但不该用。比如用户当前问的是 PyTorch 项目，系统不应该召回一个 JavaScript 项目的修复经验；用户只要求解释代码，也不应该召回自动修改代码的程序性记忆。

所以整体回答可以总结为：LLM 负责理解、反思、摘要和抽象，规则和代码负责边界、触发、结构化、校验、索引和安全。这样既利用了 LLM 的语义能力，也避免了记忆系统变成不可控的“模型随便写、随便用”。

13、如何判断一次执行经验值得写入长期记忆？成功任务才写，失败任务也写吗？

我会设计一个写入判断标准：首先判断是否可复用，其次判断是否经过验证，再判断是否有清晰适用边界，最后判断是否与已有记忆重复。如果是成功经验，可以写成正向流程；如果是失败经验，只能写成 warning、anti-pattern 或 troubleshooting note。长期记忆必须服务于未来任务决策，而不是把所有历史堆进去。

14、记忆写入时如何避免污染？错误工具调用经验被总结成记忆怎么办？

我会从写入前、写入时、写入后和复用时四个阶段控制污染。

写入前要有触发条件，不允许每次执行都自动写长期记忆。只有任务完成、用户确认、测试通过、或者系统判断产生了高价值经验时，才进入候选记忆生成。失败任务也可以进入候选，但必须标记为失败经验，不能直接作为正向策略。

写入时要做置信度和证据绑定。每条记忆都应该带上 evidence，也就是它来自哪次任务、哪些工具结果、哪些测试输出、哪些用户反馈。如果一条记忆没有证据，只是模型凭空总结，就不应该入库。比如“项目使用 pytest”必须来自 pyproject.toml、requirements.txt 或实际测试命令，而不是模型猜测。

写入时还要做类型区分。很多污染来自把情景记忆错误泛化成程序性记忆。比如“这次项目的入口文件是 app.py”只能是项目语义记忆，不能写成“Python 项目入口文件通常是 app.py”。再比如“用户这次让我不要跑测试”只是当前任务约束，不能写成“用户永远不希望跑测试”。分类错误会造成严重长期污染。

写入后要做版本管理和质量评分。记忆不是一旦写入就永久可信。每条记忆应该有置信度、更新时间、使用次数、成功次数、失败次数。如果某条记忆被复用后导致错误，就降低置信度；如果多次导致失败，就冻结或删除。如果新证据和旧记忆冲突，不能简单覆盖，要保留版本并标记旧记忆过期。

复用时也要防污染。即使一条记忆被召回，也不能无条件使用。Agent 应该判断它是否适用于当前任务、是否有足够相似的上下文、是否和当前用户指令冲突。如果冲突，当前用户指令和当前环境证据优先。

对于“错误工具调用经验被总结成记忆”的情况，我会这样处理：如果工具调用失败，比如读错路径、命令不存在、权限不足，系统应该把它标记成 tool_error，而不是成功经验。反思阶段要明确失败原因。如果失败原因是路径假设错误，那么可以写成负向经验：“不要在未确认项目结构前假设文件路径，应先 list_dir 或 search_code。”但不能写成“某个文件不存在”这种长期结论，除非当前项目上下文中已经被验证。

所以关键原则是：记忆必须带证据、带类型、带置信度、带适用边界，并且可以被更新和撤销。没有这些机制，自进化记忆很容易变成自我污染系统。

15、记忆检索时如何避免召回无关历史？用语义相似度、时间衰减、任务类型过滤，还是其他机制？

避免召回无关历史不能只靠 embedding 相似度。语义相似度只能说明“文本看起来相关”，不能说明这条记忆在当前任务中应该被使用。比如用户当前问“优化代码结构”，向量检索可能召回“优化模型训练速度”的记忆，因为都有“优化”这个词，但实际完全不是一类任务。

我会采用多阶段检索。第一步是 metadata filter，也就是先按硬条件过滤。比如当前项目 ID、语言、任务类型、memory 类型、权限模式、时间范围。当前任务是 Python 项目，就过滤掉 JavaScript 项目经验；当前任务是代码解释，就不要召回自动修改代码的 Skill 记忆；当前用户只要求只读分析，就不要召回需要 edit_file 的程序性记忆。

第二步是 hybrid retrieval，也就是语义向量召回加关键词召回。向量召回负责处理表达变化，比如“测试挂了”“pytest failed”“CI 不通过”都能召回测试失败相关记忆；关键词召回负责精确匹配，比如文件名、函数名、错误类型、框架名。Coding Agent 场景里关键词很重要，因为 ModuleNotFoundError、KV Cache、pytest、RMSNorm 这类术语不能只靠语义近似。

第三步是时间衰减。时间不是唯一依据，但它很重要。用户偏好、项目结构、依赖版本都会变化。越新的记忆通常权重越高，特别是项目状态类记忆。比如一个项目以前用 requirements.txt，后来迁移到 pyproject.toml，旧记忆就应该降权。但程序性记忆的时间衰减可以弱一些，因为“如何分析 pytest 报错”这种经验比较稳定。

第四步是上下文一致性检查。被召回的记忆要和当前任务上下文对齐。比如记忆里说项目使用 PyTorch，但当前项目文件里显示是 TensorFlow，那就不能用旧记忆。当前环境证据优先于历史记忆。记忆只能辅助判断，不能覆盖当前工具观察结果。

第五步是 LLM rerank。系统召回 top-k 记忆后，不应该全部塞进 prompt，而是让模型或 reranker 判断哪些记忆真正有用。判断依据包括：这条记忆是否直接帮助当前任务，是否有明确适用边界，是否和当前任务冲突，是否只是表面相似。最终只保留少量高价值记忆进入上下文。

第六步是按需检索，而不是每轮都全量检索。比如用户只是问一个简单概念，不需要检索项目记忆；当 Agent 要修改代码、定位项目文件、延续上次任务、使用用户偏好时，才检索相关记忆。这样可以减少噪声和 token 成本。

所以我的检索策略是：先用 metadata 做硬过滤，再用 embedding 和关键词做候选召回，再用时间衰减和质量分调整权重，最后用 LLM 或 reranker 做上下文相关性判断。核心目标不是召回最多，而是召回少量、准确、可用的记忆。

16、用户画像记忆和任务记忆如何区分？“用户喜欢简洁回答”和“某项目使用 PyTorch”分别存在哪里？

用户画像记忆和任务记忆的区别在于：用户画像描述的是用户长期稳定的偏好、习惯和约束；任务记忆描述的是某个项目、某次任务或某个上下文中的事实和经验。二者的作用范围不同，更新频率不同，风险也不同。

“用户喜欢简洁回答”应该存到用户画像记忆里，因为它是跨任务、跨项目都可能影响交互方式的长期偏好。下次用户问 RAG、Agent、代码、论文，这个偏好都可能影响回答风格。但写入这类记忆要谨慎，最好用户明确表达过，例如“以后回答都简洁一点”或多次稳定表现出这个偏好。如果只是某一次用户说“这次简单说”，那只能作为当前会话约束，不能写入长期用户画像。

“某个项目使用 PyTorch”应该存到项目语义记忆里，不应该存到用户画像。因为这不是用户本人的偏好，而是某个项目的事实。它只在这个项目上下文中有效。如果用户换到另一个 TensorFlow 项目，不能因为之前记住“用户项目使用 PyTorch”就错误假设所有项目都用 PyTorch。

还有一种情况是任务情景记忆。例如“上次用户让我修复 train.py 里的 shape mismatch，最后问题出在 batch 维度”。这不是用户画像，也不只是项目静态事实，而是某次具体任务的执行记录。它应该存到 episodic memory，并绑定项目 ID、时间、任务目标和结果。

区分时可以看三个问题。第一，这条信息是否跨项目长期有效？如果是，可能是用户画像。第二，这条信息是否只描述某个项目的事实？如果是，应该是项目语义记忆。第三，这条信息是否描述某次任务过程？如果是，应该是情景记忆。第四，这条信息是否描述一种通用操作方法？如果是，应该是程序性记忆。

比如“用户不希望在没有确认前自动修改代码”是用户画像或全局安全偏好。“brain-memory-agent 项目使用 DeepSeek API”是项目语义记忆。“上次跑 benchmark 的结果文件在 results 目录”是情景记忆或项目状态记忆。“跑 benchmark 前要先确认 loader 是否存在”是程序性经验。

这个区分很重要，因为如果把项目事实误存成用户画像，Agent 会跨项目错误泛化；如果把用户偏好误存成一次任务记忆，后续又无法复用。Memory System 的质量很大程度取决于分类是否准确。

17、Agent 的长期记忆和当前上下文如何协同？每轮都检索还是只在特定阶段检索？

长期记忆和当前上下文不是替代关系，而是互补关系。当前上下文记录的是用户当前明确给出的任务、当前工具观察结果和正在执行的计划；长期记忆提供的是历史经验、项目事实和用户偏好。执行时应该以当前上下文为主，长期记忆作为辅助。

我不会每轮都无差别检索长期记忆。因为每轮都检索会带来三个问题：第一，token 成本高；第二，容易引入无关历史；第三，历史记忆可能干扰模型对当前事实的判断。更合理的方式是按阶段、按需要检索。

在任务开始阶段，可以检索用户画像和项目语义记忆。比如用户打开一个已有项目，Agent 可以先查这个项目以前的技术栈、目录结构、常用测试命令、用户对这个项目的约束。这样可以更快建立初始上下文。

在规划阶段，可以检索程序性记忆。比如任务是“修复测试失败”，就召回以前沉淀的 debug workflow；任务是“重构函数”，就召回函数级优化 Skill 或重构经验。程序性记忆主要帮助 Agent 制定计划。

在执行阶段，不一定每轮都检索。只有当出现信息不足、工具失败、上下文超限、任务切换、或者需要使用历史经验时，才触发检索。例如连续两次工具调用失败，可以检索“类似错误处理经验”；用户说“继续上次那个实验”，可以检索上次任务情景记忆。

在总结阶段，可以决定是否写入新记忆。任务结束后，根据执行结果、测试验证、用户反馈，判断是否需要把这次经验沉淀为长期记忆。

协同时还要注意优先级。当前用户指令优先于长期用户画像，当前工具观察结果优先于历史项目记忆，安全策略优先于所有记忆。比如长期记忆里说“用户通常希望自动修复代码”，但当前用户明确说“这次不要改，只分析”，那必须服从当前指令。再比如历史记忆说测试命令是 pytest，但当前项目配置显示使用 uv run pytest，那应以当前项目文件为准。

所以我的设计是：长期记忆不是每轮强制注入 prompt，而是通过 memory router 按需检索。检索结果也不是直接使用，而是经过相关性判断、冲突检测和上下文压缩后才进入当前 prompt。这样既能利用历史经验，又不会让旧记忆污染当前任务。

18、如果长期记忆和当前用户指令冲突，Agent 应该服从谁？

这个问题的原则很清楚：当前用户显式指令优先于长期记忆，当前环境证据优先于历史记忆，系统安全规则优先于用户指令和长期记忆。长期记忆只能提供默认偏好和背景信息，不能覆盖用户当前明确表达的要求。

例如长期记忆里记录“用户喜欢简洁回答”，但当前用户说“这次详细解释”，那这次就必须详细解释。因为长期记忆表达的是默认偏好，当前指令表达的是当前任务约束，当前约束优先。

再比如长期记忆里记录“这个项目使用 PyTorch”，但当前读取项目文件发现 requirements.txt 里是 TensorFlow，或者用户明确说“这个新项目不是 PyTorch”，那么当前证据优先。Agent 应该更新或降权旧记忆，而不是坚持历史记忆。

再比如长期记忆里记录“用户通常希望自动修复代码”，但当前用户说“不要改代码，只告诉我问题在哪里”，Agent 就不能调用写文件工具。长期偏好不能覆盖当前明确限制。

还有一种冲突是用户指令和安全策略冲突。比如用户说“帮我读取 .env 里的 API key”，即使用户当前明确要求，系统也应该谨慎处理，至少需要提示敏感信息风险，默认不把密钥内容暴露进模型上下文。安全策略的优先级高于普通任务指令。

处理冲突时，我会让 Agent 做显式冲突检测。也就是说，检索到长期记忆后，先判断它和当前任务是否一致。如果一致，就作为辅助上下文；如果冲突，就标记为 conflict，并采用更高优先级的信息。如果旧记忆明显过期，还要在任务结束后触发 memory update，把旧记忆降权、归档或更新。

举个具体例子：长期记忆里存着“用户在项目 A 中使用 DeepSeek API 运行 benchmark”，现在用户在项目 B 中说“这次我要本地部署 Qwen 模型，不用 API”。Agent 应该服从当前项目 B 的要求，不应该继续建议 DeepSeek API。正确处理方式是回答：“当前任务以本地部署 Qwen 为准，之前 DeepSeek API 的设置只适用于项目 A 或历史实验。”然后在项目 B 的语义记忆里记录新的技术路线。

所以最终原则可以概括为：长期记忆是默认背景，不是硬约束；当前用户指令是当前任务约束；当前工具结果是事实依据；系统安全策略是最高边界。当它们冲突时，优先级应该是安全规则最高，其次是当前用户明确指令，其次是当前环境证据和工具 observation，然后才是长期记忆。

19. 为什么 Coding Agent 特别需要上下文压缩？

Coding Agent 比普通问答 Agent 更需要上下文压缩，因为它面对的上下文不是一段短文本，而是一个持续增长的工作现场。用户的问题、项目目录、多个代码文件、搜索结果、测试日志、报错堆栈、工具调用记录、修改 diff、历史计划、反思结果都会不断进入上下文。如果这些内容全部原样放进 prompt，很快就会超过上下文窗口，或者虽然没有超过窗口，但模型注意力会被大量无关细节稀释，导致后续决策质量下降。

代码任务还有一个特殊点：很多信息是长而稀疏的。比如一个 800 行的文件里，真正和当前 bug 有关的可能只有 30 行；一次 pytest 日志可能有几千行，关键只有最后的 traceback 和 assertion diff；一次 grep 结果可能返回几十个候选函数，真正有用的只有两个。如果不压缩，模型会消耗大量 token 处理低价值文本，同时容易抓错重点。

另外，Coding Agent 是多轮执行系统。它不是一次性回答，而是不断读文件、搜索、修改、测试、再调整。每一轮都把旧内容完整塞回 prompt，会导致上下文线性甚至指数式膨胀。前几轮的工具结果如果不整理，会变成“历史噪声”，模型可能反复引用过期判断。例如第一轮猜测 bug 在 A 文件，后面已经证明 bug 在 B 文件，但 A 文件内容还一直留在上下文里，模型可能又被旧信息干扰。

所以我做上下文压缩的目标不是简单减少 token，而是做上下文治理。它要解决四件事：第一，保留当前任务真正需要的信息；第二，把大工具结果外置化，避免 prompt 被原始数据淹没；第三，让模型可以按需恢复细节；第四，保持长任务中的状态稳定性。也就是说，压缩不是把信息丢掉，而是把信息分层组织，让模型在当前轮只看到“必要摘要”，需要细节时再检索原文。

20. 什么是大工具结果外置化？工具结果不直接放进 prompt，后续怎么访问？

大工具结果外置化的意思是：当工具返回的内容很大时，不把完整结果直接塞进模型上下文，而是把原始结果存到外部存储里，只把一个短摘要、索引信息和可回溯引用放进 prompt。模型当前只看到“这个结果是什么、关键结论是什么、如果需要细节应该如何取回”，而不是看到完整的几千行原文。

比如 Agent 读取了一个 1000 行的 model.py 文件。如果把完整文件直接放进 prompt，代价很高，而且大部分行当前未必有用。更合理的做法是把完整文件内容存到外部 context store，给它一个引用 ID，例如：

外置化的关键不是“丢弃内容”，而是“原文可恢复，prompt 只放索引和摘要”。这类似 RAG 里的文档索引，也类似操作系统里的分页：当前工作区只加载活跃页面，其他内容留在外部，需要时再调入。对 Coding Agent 来说，这可以显著降低 token 成本，也能让模型的注意力集中在当前决策相关的信息上。

21. “缓存友好型占位压缩”是什么意思？Prompt Cache 如何发挥作用？

缓存友好型占位压缩指的是，在构造 prompt 时，把稳定不变的大块上下文放在固定位置，并用稳定的占位符表示外部内容，避免每一轮 prompt 都发生大幅变化。这样做可以提高 Prompt Cache 的命中率，降低 token 成本和延迟。

很多模型服务会对相同的 prompt 前缀做缓存。如果每一轮都把工具结果、日志、文件内容直接拼到 prompt 前面，那么 prompt 每轮都变化，缓存命中率就很低。更好的方式是把系统提示词、工具说明、项目静态摘要、Skill 说明这些稳定内容放在前缀部分，并保持格式稳定；动态变化的内容放在后面，而且尽量用短占位符表达。

比如不要每次都这样构造 prompt：

1
2
3
4
5
6

系统规则...
工具说明...
完整 model.py 1000 行...
完整 train.py 800 行...
完整 pytest 日志 5000 行...
当前问题...

这样每轮都会变化，而且很长。

更合理的是：

1
2
3
4
5
6
7
8

系统规则...
工具说明...
项目摘要：
- <FILE_REF id="file:model.py:v3" summary="定义模型结构，Attention 相关逻辑在 120-210 行">
- <FILE_REF id="file:train.py:v2" summary="训练入口，loss 计算在 88-140 行">
- <LOG_REF id="pytest:run_12" summary="test_login_expired_token 失败，expected 401 got 200">
当前任务状态...
当前轮问题...

这里的 <FILE_REF>、<LOG_REF> 就是占位压缩。它们有几个特点：第一，长度短；第二，格式稳定；第三，能指向外部原文；第四，模型能理解需要细节时应该调用工具读取。

Prompt Cache 在这里发挥作用的方式是：系统 prompt、工具 schema、项目摘要结构、Skill 描述这些内容尽量保持稳定，减少每轮重组。动态内容只追加在尾部，或者以固定模板更新。这样前缀可以被缓存，后续每轮只需要处理新增内容。

面试时可以强调一点：缓存友好不只是省钱，它还提升了长任务稳定性。因为 prompt 结构稳定，模型每轮看到的信息布局一致，决策模式也更稳定。如果每轮上下文拼接方式都不同，模型更容易遗漏状态或误解引用关系。

22. “摘要预览—占位替换—按需检索—超限兜底”流程怎么走？

这个流程是我设计的上下文治理闭环。它的目标是：当工具结果或历史上下文过大时，先给模型一个可理解的摘要预览，用占位符替换原始内容；如果模型后续需要细节，再按需检索；如果上下文仍然超限，就进一步降级压缩，保证任务继续执行。

第一步是摘要预览。每次工具返回大内容后，系统先判断结果大小。如果结果很短，比如几十行，就可以直接放进上下文。如果结果很长，比如完整文件、长日志、大量搜索结果，就先生成摘要。摘要不是普通概括，而是面向任务的结构化摘要。例如代码文件摘要要包括文件功能、主要类和函数、与当前任务相关的片段、关键行号；测试日志摘要要包括失败测试、异常类型、关键报错、可能关联文件；搜索结果摘要要包括命中位置、候选相关性和建议下一步阅读哪些文件。

第二步是占位替换。原始内容不直接进入 prompt，而是替换成一个引用块。例如：

1
2
3
4

[CTX:file:src/auth.py:v5]
summary: 认证相关逻辑，包含 verify_token、refresh_token、login_user。
relevant_ranges: 42-88, 130-176
full_content_available: true

这个占位块告诉模型：完整内容存在，但当前只展示摘要。模型如果需要具体代码，可以读取相应行。

第三步是按需检索。当模型判断当前摘要不够用时，可以主动调用工具恢复细节。例如它要修改 verify_token，就不能只依赖摘要，必须读取函数原文。于是调用：

1
2
3
4
5
6
7

{
  "tool": "read_context",
  "arguments": {
    "context_id": "file:src/auth.py:v5",
    "line_range": [42, 88]
  }
}

恢复出来的片段可以临时进入上下文，用于当前轮推理或编辑。任务结束后，这段细节又可以被重新压缩成摘要，避免一直占用窗口。

第四步是超限兜底。如果上下文仍然接近上限，系统要进一步压缩。兜底策略包括：丢弃已完成步骤的原始 observation，只保留结论；把旧对话压缩成 task state；只保留最近 N 轮关键动作；把多个文件摘要合并成项目级摘要；把低相关记忆移出当前 prompt；必要时重新构造一个 clean context，只保留用户目标、当前计划、已确认事实、待处理问题和可恢复引用。

所以这套流程的核心是：摘要让模型知道有什么，占位让上下文保持短，按需检索保证细节可恢复，超限兜底保证任务不会因为上下文爆炸而崩掉。它比简单截断更可靠，因为截断会随机丢失信息，而分层压缩能保留结构和可追溯性。

23. 工具返回一个很大的代码文件时，你会怎么压缩？

如果工具返回一个很大的代码文件，我不会直接做普通自然语言摘要，因为代码压缩需要保留结构信息。我的做法通常是分层压缩：先做文件级结构摘要，再做符号级摘要，然后保留与当前任务相关的局部片段，最后生成可检索索引。

文件级摘要主要回答：这个文件负责什么，包含哪些 import，定义了哪些类、函数、全局变量，核心调用关系是什么。例如：

2

4

src/model.py:
该文件实现类 Llama 的 Transformer 模型结构。
主要符号：
- RMSNorm: 归一化模块
- RotaryEmbedding: RoPE 位置编码
- Attention: 多头注意力和 KV Cache
- FeedForward: SwiGLU FFN
- TransformerBlock: Attention + FFN
- LlamaModel: token embedding、blocks、lm_head

符号级摘要则针对每个类和函数生成更细粒度说明。例如：

Attention.forward(x, start_pos, freqs_cis, mask):

如果当前任务和 KV Cache 有关，就进一步保留相关行号和局部片段，而不是保留整个文件：

1
2
3

relevant_ranges:
- lines 88-135: Attention 初始化，包括 q_proj/k_proj/v_proj/o_proj
- lines 136-220: Attention.forward，包括 KV Cache 更新和 attention 计算

对于代码文件，最好使用 AST 或简单 parser 辅助压缩。Python 可以用 ast 抽取类、函数、参数、docstring、调用关系；JavaScript/TypeScript 可以用 tree-sitter；如果没有 parser，也可以用正则和缩进结构做近似。这样生成的摘要比 LLM 直接概括更稳定。

还要保留 checksum 或版本号。因为代码会被修改，如果摘要对应的是旧版本，后续就可能误导模型。所以占位符要带版本：

1
2

summary_generated_at: after_read_step_8

一旦文件修改，旧摘要要标记过期，重新生成或局部更新。

面试时可以这样总结：大代码文件压缩不是简单“总结一下”，而是保留文件结构、符号表、关键函数、调用关系、相关行号和版本引用。当前任务相关的函数可以保留原文，不相关部分只保留摘要。这样既降低 token，又不丢失代码修改所需的精确信息。

24. 摘要压缩会丢信息，如果后续需要被压缩掉的细节，系统如何恢复？

摘要一定会丢信息，所以压缩系统必须从一开始就设计“可恢复”。如果压缩只是把原文总结后丢掉，那在 Coding Agent 场景里是不可接受的，因为代码修改经常需要精确到某一行、某个变量名、某个异常分支。

我的做法是，压缩时永远不删除原始工具结果，而是把原文放到外部 context store，并给摘要绑定引用 ID、文件路径、行号范围、版本号和检索接口。摘要只是当前 prompt 的轻量视图，原文仍然可以通过工具恢复。

当模型后续需要细节时，有几种恢复方式。第一种是按引用 ID 恢复，比如模型已经知道 file:src/auth.py:v3，就直接读取某个行号范围。第二种是按符号恢复，比如读取 verify_token 函数的完整定义。第三种是按关键词恢复，比如在外部结果里搜索 expired_token。第四种是按调用链恢复，比如从当前函数跳到它调用的函数定义。

例如摘要里写：

1

verify_token 函数负责解析 token，过期判断在 72-83 行。

如果模型要修改过期判断，它必须调用：

1
2
3
4
5
6
7
8

{
  "tool": "read_file",
  "arguments": {
    "path": "src/auth.py",
    "start_line": 65,
    "end_line": 90
  }
}

而不是基于摘要直接改。因为摘要不包含完整代码，直接修改容易出错。

如果上下文中只有旧摘要，但文件已经变了，系统还要做版本检查。比如摘要版本是 hash=abc123，当前文件 hash 是 def456，那就不能直接使用旧摘要，必须重新读取文件或更新摘要。

还有一种恢复是“局部反压缩”。当某个细节被恢复并使用后，不一定要让它永久留在上下文里。当前轮用完后，系统可以把它重新压缩成更精确的局部摘要。例如：

1

已确认 verify_token 在 78 行错误地使用 < 而不是 <= 判断过期时间。

这样既恢复了必要细节，又避免上下文再次膨胀。

所以回答这个问题的关键是：压缩不能是不可逆压缩，而应该是可追溯、可检索、可恢复的分层压缩。真正删除的应该是低价值副本，不是原始证据。

25. 上下文压缩和 RAG 有什么关系？它们是同一类问题还是不同层面的机制？

上下文压缩和 RAG 有相似点，但不是同一个问题。它们都在解决“模型上下文窗口有限，不能把所有信息一次性塞进去”的问题，也都涉及索引、召回、筛选和重组。但是二者的使用场景和信息来源不同。

RAG 主要解决外部知识注入问题。它面对的是文档库、知识库、网页、论文、项目文档等相对外部的信息。用户问一个问题，系统从知识库检索相关片段，然后把片段放进 prompt，帮助模型回答。RAG 的核心问题是：怎么切片、怎么 embedding、怎么召回、怎么 rerank、怎么保证答案忠实于检索内容。

上下文压缩主要解决 Agent 执行过程中的上下文膨胀问题。它面对的是当前任务运行中产生的信息，比如工具结果、文件内容、日志、历史动作、计划状态、diff、反思记录。它的核心问题是：哪些信息继续留在当前 prompt，哪些信息外置化，哪些信息摘要化，后续如何恢复细节，如何保证长任务状态不丢失。

所以二者可以组合，但层级不同。RAG 更像是“从外部知识库取信息”，上下文压缩更像是“管理 Agent 自己执行过程中产生的信息”。在 Coding Agent 中，读过的文件、测试日志、工具结果可以被外置化并建立索引，这时上下文压缩内部也会用到 RAG 式检索。但它检索的是工作记忆和执行轨迹，不一定是传统知识库。

可以这样类比：RAG 是外部知识检索系统，Context Compression 是内部工作记忆管理系统。RAG 解决“我需要知道什么外部资料”，上下文压缩解决“我已经看过和做过这么多东西，当前轮应该保留什么”。二者共享检索技术，但服务的 Agent 层面不同。

26. 为什么选择中心化多 Agent 协作，而不是多个 Agent 自由通信？

我选择中心化多 Agent 协作，是因为 Coding Agent 场景对一致性、安全性和可控性要求很高。多个 Agent 自由通信看起来更智能，但实际工程上很容易出现状态不一致、重复工作、权限失控、冲突修改和责任边界不清的问题。

中心化架构里有一个主 Agent，负责统一理解用户目标、制定计划、分配任务、审批工具调用、合并结果和控制最终输出。子 Agent 只负责受控执行某个局部任务，比如分析某个模块、生成测试、检查某个 bug 原因、给出重构建议。子 Agent 的结果返回给主 Agent，由主 Agent 决定是否采用。

这样做的好处是状态集中。所有关键状态都在主 Agent 或 central state store 里维护，包括任务目标、当前计划、已读文件、已修改文件、测试结果、权限边界。如果让多个 Agent 自由通信，每个 Agent 都可能持有不同版本的上下文，最后很难判断谁的结论是最新的。

第二个好处是安全可控。子 Agent 不应该随便读写文件或执行命令。通过中心化控制，主 Agent 可以限制子 Agent 的工具权限和路径范围。例如一个子 Agent 只允许读取 src/auth/ 目录，另一个只允许分析 tests/ 目录。子 Agent 的写操作必须经过主 Agent 审批，避免并发乱改代码。

第三个好处是冲突更容易处理。多个 Agent 如果都能自由修改文件，可能同时改同一个函数，最后产生冲突。中心化架构下，主 Agent 可以规定任务分片、锁定文件、收集 patch，再统一合并。

第四个好处是输出质量更稳定。多个 Agent 自由讨论可能产生很多中间观点，但用户最终需要一个明确、可靠的答案。中心化主 Agent 可以过滤子 Agent 的冗余结果、冲突结论和低质量建议，统一形成最终回答。

所以我的观点是：多 Agent 在 Coding 场景中应该是“中心化调度下的并行能力扩展”，而不是“多个模型自由聊天”。前者更工程化，后者更容易失控。

27. 主 Agent 和子 Agent 的职责边界是什么？子 Agent 能不能自己调用工具、修改代码？

主 Agent 的职责是全局控制，子 Agent 的职责是局部执行。主 Agent 负责理解用户目标、拆解任务、决定执行顺序、维护全局状态、分配子任务、控制权限、合并结果、处理冲突和输出最终答案。它相当于项目里的 coordinator 或 controller。

子 Agent 则只处理明确边界内的子任务。例如主 Agent 可以派一个子 Agent 分析测试失败原因，派另一个子 Agent 阅读某个模块并总结调用链，派第三个子 Agent 生成候选 patch。子 Agent 不应该擅自改变全局计划，也不应该越界访问无关文件。

子 Agent 能不能调用工具，要看权限设计。我的倾向是可以调用受限工具，但不能拥有完整工具权限。比如分析型子 Agent 可以调用 read_file、search_code，但不能调用 edit_file；测试型子 Agent 可以运行指定测试命令，但不能执行任意 shell；修改型子 Agent 可以生成 patch proposal，但真正写入文件要经过主 Agent 或系统审批。

子 Agent 能不能修改代码，也要分模式。如果系统处于只读模式，子 Agent 不能修改。如果系统允许修改，子 Agent 最好也不要直接写工作区，而是生成 patch 或在隔离分支、worktree、sandbox 中修改，然后交给主 Agent 审查。主 Agent 审查内容包括修改范围是否符合任务、是否影响其他模块、是否通过测试、是否和其他子 Agent 的修改冲突。

所以主 Agent 和子 Agent 的边界可以概括为：主 Agent 拥有全局目标和最终控制权；子 Agent 拥有局部任务和受限工具权。子 Agent 可以探索和提出建议，但不能擅自扩大任务范围，不能绕过权限系统，不能直接覆盖主 Agent 的最终决策。

28. “不移交控制权、最小化结果传递、工具权限约束、路径边界限制”分别解决什么风险？

“不移交控制权”解决的是多 Agent 失控问题。主 Agent 始终是唯一的全局控制者，子 Agent 只是被调用的执行单元。这样可以避免子 Agent 自己继续拆任务、再调用其他 Agent、再扩大范围，导致任务链条不可追踪。尤其在 Coding 场景里，如果控制权不断转移，很容易出现不知道哪个 Agent 做了什么、为什么修改某个文件、最终责任归属不清的问题。

“最小化结果传递”解决的是上下文污染和信息泄露问题。子 Agent 执行完任务后，不应该把所有读过的文件、完整日志和中间推理都传回主 Agent。它应该只返回结构化结果，例如发现了什么、依据是什么、建议做什么、相关文件和行号在哪里。如果把大量原始内容都传回主 Agent，会造成上下文膨胀，也可能把无关信息或敏感信息带入全局上下文。

“工具权限约束”解决的是越权操作问题。不同子 Agent 只能使用完成任务所需的最小工具集合。比如代码解释子 Agent 只需要读文件，不需要写文件；测试分析子 Agent 可以运行测试，但不应该执行 rm、curl、sudo；重构建议子 Agent 可以生成 patch，但不一定能直接 apply。这样即使某个子 Agent 被 prompt injection 诱导，也无法执行高风险操作。

“路径边界限制”解决的是访问范围失控问题。子 Agent 只能访问与子任务相关的目录或文件。比如负责 auth 模块的子 Agent 只能看 src/auth/ 和相关测试文件，不能读取用户主目录、.env、.ssh 或其他项目文件。路径边界也可以减少无关检索，提高效率。

这四个设计合起来，就是让多 Agent 变成受控并行系统，而不是一组自由行动的模型。主 Agent 控制目标和合并，子 Agent 最小权限执行，结果最小化返回，文件访问被限制在边界内。这样可以同时提升并行效率和安全性。

29. Fork / Worktree / Agent Team 在 Coding Agent 里分别适合什么场景？

Fork、Worktree 和 Agent Team 都是多 Agent 协作时的隔离机制，但适用场景不同。

Fork 更适合方案探索。比如主 Agent 不确定某个 bug 有两种修复方向，一种是改业务逻辑，一种是改配置。可以 fork 出两个独立分支，让两个 Agent 分别尝试，然后比较 diff、测试结果和风险。Fork 的优势是隔离彻底，不同方案互不影响；缺点是合并成本高，适合探索性任务，而不是每个小改动都 fork。

Worktree 更适合并行开发和验证。Git worktree 可以让同一个仓库在不同目录下检出不同分支。多个 Agent 可以在不同 worktree 中并行修改，不会直接冲突主工作区。比如一个 Agent 修复 auth 模块，另一个 Agent 生成 tests，第三个 Agent 做文档更新。最后主 Agent 统一看每个 worktree 的 diff 和测试结果，再决定合并哪些修改。Worktree 的优势是接近真实工程协作，适合复杂代码任务。

Agent Team 更适合角色分工。它不一定要求每个 Agent 都有独立分支，而是按职责划分。例如 Planner Agent 负责拆解任务，Reader Agent 负责代码阅读，Debugger Agent 负责分析错误，Patch Agent 负责生成修改，Reviewer Agent 负责审查 diff，Tester Agent 负责运行测试。Agent Team 的核心是能力分工，不一定是代码隔离。

三者可以组合使用。例如一个复杂 bug 修复任务中，主 Agent 先组织 Agent Team 做分析；当出现两个候选修复方案时，用 Fork 或 Worktree 隔离实验；最后由 Reviewer Agent 审查 diff，由主 Agent 合并最优方案。

如果面试官问具体场景，可以这样答：Fork 适合多方案试错，Worktree 适合多任务并行修改，Agent Team 适合角色化协作。它们不是互斥关系，而是不同层面的协作机制。

30. 如果两个子 Agent 同时修改同一个文件，如何处理冲突？

如果两个子 Agent 同时修改同一个文件，不能让它们直接写同一个工作区。更稳妥的设计是让每个子 Agent 在独立 patch、branch 或 worktree 中修改，然后由主 Agent 统一合并。冲突处理分为预防、检测、合并和回滚四个阶段。

预防阶段，主 Agent 在分配任务时尽量做文件级或模块级分片。例如一个 Agent 负责 src/auth.py，另一个 Agent 负责 tests/test_auth.py。如果确实需要多个 Agent 修改同一个文件，主 Agent 要明确它们负责的不同函数或行号范围，并给文件加逻辑锁，避免同时编辑同一区域。

检测阶段，系统要比较每个子 Agent 的 diff。如果两个 diff 修改了同一行或相邻代码块，就标记为冲突。如果修改不同区域，也要做语义检查，因为即使 Git 不冲突，逻辑也可能冲突。例如一个 Agent 改了函数签名，另一个 Agent 还按旧签名调用。

合并阶段，主 Agent 不能简单按时间顺序覆盖，而要结合任务目标和测试结果判断。可以先合并低风险、局部修改，再合并影响范围大的修改。对于冲突 patch，可以让 Reviewer Agent 或主 Agent 生成合并版本，然后运行测试验证。

回滚阶段，如果合并后测试失败，要能恢复到合并前状态。每个子 Agent 的修改都应该以 patch 形式记录，方便撤销。不能让 Agent 直接不可逆地修改大量文件。

我的系统会避免多个子 Agent 直接写同一个工作区。子 Agent 只生成 patch 或在隔离 worktree 中修改，主 Agent 统一做 diff 合并。如果出现同文件同区域冲突，优先用任务目标、修改范围、测试结果和风险评估来选择或合并。如果无法自动判断，就请求用户确认。所有修改都要有 diff 和回滚点。

31. 多 Agent 并行一定能提升效率吗？什么时候反而会降低稳定性？

多 Agent 并行不一定提升效率。它只有在任务可以清晰拆分、子任务之间依赖较弱、结果容易合并时才有价值。如果任务本身高度串行，或者上下文共享成本很高，多 Agent 反而会降低稳定性。

适合多 Agent 的场景包括：大项目中多个模块可以独立分析；同一个 bug 有多个候选原因，可以并行验证；需要一个 Agent 写 patch、另一个 Agent 做 review；需要同时生成测试和文档；需要比较多种实现方案。这些场景下，多 Agent 可以提高探索速度和覆盖面。

不适合多 Agent 的场景包括：用户问题很简单，一个 Agent 就能完成；任务依赖强，必须先读 A 文件才能决定是否看 B 文件；多个 Agent 都需要修改同一核心文件；项目上下文很复杂但无法清晰切分；没有足够的测试来验证多个修改；模型能力较弱，子 Agent 之间产生大量矛盾结论。这些情况下，多 Agent 会带来额外协调成本。

多 Agent 降低稳定性的原因主要有几个。第一，状态不一致。不同 Agent 看到的上下文不同，可能得出冲突结论。第二，重复工作。多个 Agent 可能都去读同一批文件，浪费 token 和时间。第三，修改冲突。多个 Agent 并行改代码，合并成本上升。第四，责任不清。最终 bug 是哪个 Agent 引入的，不容易追踪。第五，噪声变多。主 Agent 要处理多个子 Agent 的输出，如果没有强过滤，反而会被大量中间结果干扰。

所以我的设计原则是：多 Agent 不是默认开启，而是按任务复杂度和可并行性触发。简单任务单 Agent 更稳定；复杂任务可以多 Agent，但必须中心化调度、最小权限、隔离执行、结构化返回、统一合并。多 Agent 的目标不是“Agent 越多越智能”，而是在可控边界内扩大搜索和验证能力。

32. RAG pipeline 怎么完整走一遍？

RAG 全称是 Retrieval-Augmented Generation，意思是：模型回答问题前，不只依赖自己参数里的知识，而是先去外部知识库检索相关内容，再基于检索结果生成答案。

完整流程可以分成两条线：离线建库 和 在线问答。

离线建库阶段，第一步是文档加载。系统先把 PDF、Word、网页、Markdown、数据库内容、代码文档等资料读进来。第二步是文档清洗，去掉页眉页脚、目录、乱码、重复内容、无意义空行。第三步是文档切片，也就是把长文档拆成较小的 chunk。第四步是 embedding，把每个 chunk 转成向量。第五步是存入向量数据库，同时保存原文、标题、来源、页码、时间、文档类型等 metadata。

在线问答阶段，用户输入一个问题后，系统先对问题做预处理，比如改写 query、补充上下文、识别意图。然后把 query 转成向量，到向量库里检索相似 chunk。检索回来后，通常还要做 rerank，也就是重新排序，选出最相关的几个片段。之后把这些片段和用户问题一起拼成 prompt，让大模型生成答案。最后系统可以做后处理，比如加引用、检查答案是否基于文档、判断有没有幻觉。

一句话总结就是：

1

文档加载 → 清洗 → 切片 → embedding → 入库 → 用户提问 → query 改写 → 检索 → rerank → 拼 prompt → 生成答案 → 引用与校验

面试时可以补一句：RAG 的核心不是“把文档塞给模型”，而是要保证 检索到正确内容，并让模型只基于这些内容回答。

33. 文档切片策略有哪些？

文档切片就是把长文档拆成适合检索的小块。切太大，检索不准；切太小，语义不完整。所以切片策略会直接影响 RAG 效果。

fixed-size chunk 是固定长度切片，比如每 500 个 token 切一块，重叠 50 个 token。它的优点是实现简单、稳定、适合通用文档。缺点是容易把一个完整语义切断，比如一个表格、一段定义、一个流程被拆到两个 chunk 里，导致检索回来时上下文不完整。

例如：

1
2

chunk_size = 500 tokens
overlap = 50 tokens

这种方式适合快速搭建 baseline。

semantic chunk 是语义切片。它不是按固定长度硬切，而是根据段落、句子、语义边界来切。比如一个概念解释、一段实验方法、一个代码函数尽量保留在同一个 chunk 里。优点是语义完整，模型回答时更容易理解。缺点是实现复杂，chunk 大小不稳定，有些片段可能过长，需要额外控制。

比如论文里：

1
2
3

一整段 Method 尽量放在一起
一个公式解释尽量不拆开
一个代码函数尽量不从中间截断

section-based chunk 是按文档结构切，比如按标题、章节、小节、列表、表格切。它适合结构清晰的文档，比如论文、说明书、技术文档、法律合同。优点是天然保留层级结构，可以保存标题路径，例如：

1

文档标题 > 第 3 章 实验设置 > 3.2 数据集

这样检索时不仅有正文，还有上下文位置。缺点是如果章节太长，还要在章节内部继续切；如果文档结构混乱，效果会下降。

简单对比：

1
2
3

fixed-size：简单稳定，但可能切断语义
semantic：语义完整，但实现复杂
section-based：适合结构化文档，但依赖标题质量

工程上通常会混合使用。比如先按章节切，再在章节内按语义或固定 token 切，并加 overlap。

34. 召回效果不好，从哪些环节排查？

召回效果不好，就是用户问的问题和检索出来的文档不匹配。排查时不要只怪模型，要从整个 retrieval pipeline 查。

首先看 embedding 模型。如果 embedding 模型质量差，或者中文、英文、代码、专业术语支持不好，向量相似度就不准。比如用户问“幻觉检测”，文档里写“hallucination verification”，模型如果跨语言语义对齐不好，就可能检索不到。

其次看 chunk size。chunk 太小，信息不完整；chunk 太大，里面混杂太多内容，向量表示会变模糊。比如一个 chunk 里同时有背景、方法、实验、结论，检索时它的语义中心不清楚。一般要根据文档类型调 chunk size，技术文档可以小一点，论文方法段可以稍大一点。

第三看 top-k。top-k 太小，可能漏掉正确片段；top-k 太大，又会带来噪声。比如 top-k=3 时可能没召回关键证据，top-k=20 时虽然召回了，但无关内容太多，模型生成时被干扰。所以通常会先召回较多，比如 top-20，再 rerank 选 top-5。

第四看 query rewrite。用户的问题可能很短、很口语化、缺少关键词。比如用户问“这个怎么评估”，但知识库里写的是“RAG evaluation metrics”。这时需要 query rewrite，把问题改写成更适合检索的形式。尤其多轮对话里，用户说“这个方法”，系统要补全“这个”指代的对象。

第五看 rerank。初始向量检索只看语义相似，不一定最适合回答。reranker 会把 query 和候选 chunk 放在一起重新判断相关性。它能把真正能回答问题的片段排到前面。没有 rerank 时，经常出现“看起来相关但不能回答”的 chunk 排在前面。

第六看 metadata filter。metadata 是文档来源、时间、章节、作者、项目名、类型等信息。比如用户问“LoCoMo 实验结果”，就应该过滤到 LoCoMo 相关文档；用户问“最新版本”，就应该优先检索最近文档。如果不加 metadata filter，可能召回旧版本、错误项目或无关来源。

排查顺序可以这样说：

1

先看文档有没有入库 → 再看切片是否合理 → 再看 embedding 是否适配 → 再看 query 是否需要改写 → 再看 top-k 是否合适 → 再看 rerank 是否有效 → 最后看 metadata filter 是否过滤错了

注意 metadata filter 也可能造成漏召回。如果过滤条件太严格，比如只搜某个目录，但答案在另一个目录，就会把正确内容排除掉。

35. RAG 中“召回正确但回答错误”可能是什么原因？

召回正确但回答错误，说明 retrieval 阶段没问题，问题出在 generation 或 prompt 组织阶段。

第一种原因是模型没有真正使用检索内容。它可能根据自己的参数知识回答，而不是按文档回答。这会导致答案和文档不一致。

第二种原因是 prompt 写得不好。比如 prompt 只说“根据以下内容回答”，但没有强制要求“不知道就说不知道”“必须引用原文证据”。模型就可能自由发挥。

第三种原因是检索片段太多，噪声混在里面。正确片段虽然召回了，但旁边还有很多无关片段，模型注意力被干扰，最后基于错误片段回答。

第四种原因是 chunk 缺少上下文。召回的片段本身相关，但缺少前后文，模型误解了它。例如片段里说“该方法效果较差”，但前文限定的是“在小样本场景下”，如果前文没召回，模型可能泛化成所有场景都差。

第五种原因是多个片段之间有冲突。比如不同版本文档给出不同结论，模型没有判断哪个更新、更权威。

第六种原因是问题需要推理，不是简单摘抄。检索片段里有 A 和 B，但答案需要组合推理。模型可能推理错。

第七种原因是引用不忠实。模型写了一个答案，然后随便挂了一个引用，看起来有依据，实际引用内容并不支持答案。

解决方法是：减少无关片段、增强 rerank、改进 prompt、要求答案逐句有证据、加入 citation check、对冲突文档做版本判断。如果文档不足以回答，就让模型明确说“不足以判断”。

36. 如何判断检索片段有用还是无用？

判断片段有没有用，核心标准是：这个片段能不能直接支持回答用户问题。

不能只看“语义相似”。有些片段看起来相关，但不能回答问题。例如用户问“RAG 怎么评估”，检索到一段“RAG 是什么”，它相关，但对评估问题帮助有限。

我会把片段分成三类：

1
2
3

有用：能直接回答问题或提供关键证据
部分有用：提供背景，但不能单独回答
无用：只是词相似，不能支持答案

判断方法可以结合规则和 LLM。

规则适合判断硬条件。比如用户问某个项目、某个时间、某个指标，片段 metadata 不匹配，就降权。用户问“2026 结果”，片段来自 2023，就可能无用。用户问“LoCoMo”，片段不包含 LoCoMo，也没有语义关联，就降权。

LLM 适合判断语义支持关系。可以让模型对每个 chunk 打标签：

1
2
3
4

这个片段是否回答了问题？
支持哪一句答案？
是否只是背景？
是否存在冲突？

例如输入：

1
2

问题：RAG 如何评估？
片段：介绍 Recall@k、MRR、faithfulness、answer correctness。

模型判断：有用。

如果片段是：

1

片段：介绍 Transformer attention。

模型判断：无用。

更严格的做法是让模型输出 evidence mapping，也就是每个有用片段对应答案中的哪一点。如果一个片段无法支撑任何答案句子，就不要放进最终 prompt。

面试时可以这样回答：我不会简单把 top-k 全部交给生成模型，而是会先做片段级过滤。规则负责过滤明显不匹配的文档，LLM 或 reranker 负责判断语义支持关系。最终只保留能直接支持答案的片段，背景片段少量保留，无用片段剔除。

37. 知识库没有答案时，RAG 系统应该怎么回答？如何降低幻觉？

RAG 系统应该明确说：当前知识库没有足够信息回答，而不是编造。

正确回答方式是：

1

根据当前检索到的资料，无法确定答案。已有资料只说明了 A 和 B，但没有说明 C。因此不能给出确定结论。

如果可以提供下一步建议，可以说：

1

需要补充某某文档、实验结果、配置文件或原始数据后才能判断。

降低幻觉要从三层做。

第一层是检索阶段。系统要判断有没有召回足够相关的证据。如果 top-k 片段相关性都很低，应该触发 no-answer，而不是继续生成。

第二层是生成阶段。prompt 要明确要求模型只基于检索内容回答。如果检索内容不支持答案，必须说不知道。不能用模型自身知识补全关键事实。

第三层是校验阶段。生成后检查答案中的关键句是否能被检索片段支持。如果某句话没有证据，就删除或标记不确定。

可以设置一个 no-answer 判断：

1
2
3
4

如果最高相关片段分数低于阈值 → 不回答
如果有用片段数量为 0 → 不回答
如果片段只能提供背景，不能支持结论 → 不回答
如果多个片段互相冲突且无法判断权威性 → 说明冲突，不给确定答案

面试回答可以这样说：RAG 的价值不是任何问题都回答，而是在知识库有证据时回答，没有证据时拒答或说明信息不足。可信 RAG 必须允许 no-answer。

38. 如何评估 RAG 系统？retrieval metrics 和 generation metrics 有什么区别？

RAG 评估要分两部分：检索评估和生成评估。

retrieval metrics 评估的是“有没有把正确资料找回来”。它不关心最终答案写得好不好，只看检索阶段。

常见指标有：

1
2
3
4
5

Recall@k：正确文档是否出现在 top-k 里
Precision@k：top-k 里有多少是真相关
MRR：第一个正确结果排在第几位
NDCG：相关结果排序是否合理
Hit Rate：是否至少命中一个正确片段

比如用户问题需要文档 A，系统 top-5 检索到了 A，那么 Recall@5 命中。如果 A 排第一，MRR 就高；如果 A 排第十，MRR 就低。

generation metrics 评估的是“最终答案好不好”。它关心答案是否正确、是否完整、是否忠实于证据。

常见指标有：

1
2
3
4
5

Answer Correctness：答案是否正确
Faithfulness：答案是否忠实于检索内容
Completeness：答案是否覆盖问题要点
Citation Accuracy：引用是否真的支持答案
Hallucination Rate：是否编造了文档没有的信息

两者区别很简单：

1
2

retrieval metrics 看找得准不准
generation metrics 看答得对不对

一个系统可能检索很好，但生成错误；也可能生成模型很强，但检索不到正确文档，最后只能瞎答。所以 RAG 评估必须拆开看。

更完整的评估还可以看系统指标：

1
2
3
4
5
6

延迟
token 成本
召回耗时
rerank 耗时
拒答准确率
用户满意度

面试时可以补一句：如果我是排查系统问题，我会先看 retrieval。如果正确文档没进 top-k，先修检索；如果正确文档进来了但答案错，重点修 prompt、rerank、引用和 faithfulness check。

39. 答案必须带引用，如何保证 citation faithfulness？

Citation faithfulness 指的是：答案里的引用必须真的支持答案，而不是随便挂一个来源。

要保证 citation faithfulness，第一步是让每个 chunk 保留来源信息，包括文档名、页码、章节、行号、URL、时间。没有来源信息，就无法可靠引用。

第二步是生成答案时要求模型按证据回答。不要让模型先写答案再随便加引用，而是要求每个关键结论都绑定证据片段。

例如：

1
2
3

结论 A 来自 chunk 1
结论 B 来自 chunk 3
结论 C 没有证据，不能写

第三步是做引用校验。生成后检查每个带引用的句子是否被对应 chunk 支持。如果答案说“方法 A 优于方法 B”，但引用片段只介绍了方法 A，没有比较 B，这个引用就是不忠实。

第四步是限制模型使用未检索内容。如果答案中的实体、数字、结论没有出现在检索片段中，要么删除，要么标注“不确定”。

第五步是处理多引用。一个结论可能需要多个片段支持。例如实验结果来自表格，实验设置来自方法部分。这时要引用多个来源，而不是只引一个。

可以设计一个后处理流程：

1

答案拆句 → 每句抽取 claims → 为每个 claim 找支持 chunk → 判断支持/不支持/矛盾 → 删除无支持 claim → 输出带引用答案

面试时可以这样回答：我会把引用当成证据链，而不是装饰。每个 chunk 入库时保留来源；生成时要求结论绑定 chunk；生成后做 claim-level citation check。引用不能支持的句子要删除或改成不确定表达。

40. RAG 和 Agent 结合时，RAG 是工具，还是 Agent 内部模块？两种设计有什么区别？

RAG 和 Agent 结合有两种常见设计。

第一种是把 RAG 当成 工具。也就是 Agent 有一个工具叫 retrieve_knowledge 或 search_docs。当 Agent 判断自己需要外部知识时，就调用这个工具。工具返回相关文档片段，Agent 再基于片段回答或继续执行。

这种设计的优点是灵活。Agent 可以自己决定什么时候检索、检索什么、检索几次、是否改写 query。适合复杂任务，比如代码修复、研究助手、多步问答。缺点是对 Agent 能力要求更高。如果 Agent 判断错了，可能该检索时不检索，或者检索 query 写得不好。

流程是：

1

用户问题 → Agent 判断需要知识 → 调用 RAG 工具 → 获得片段 → Agent 分析 → 可能再次检索 → 生成答案

第二种是把 RAG 当成 Agent 内部模块。也就是每次用户问题进来，系统自动先检索，再把检索结果交给 Agent 或 LLM。Agent 不需要决定是否检索，RAG 是固定 pipeline 的一部分。

这种设计的优点是稳定、简单、可控。适合标准知识库问答，比如企业文档问答、客服问答、规章制度查询。缺点是不够灵活。即使问题不需要检索，也可能检索；复杂多步任务中，它不一定知道什么时候需要再次检索。

流程是：

1

用户问题 → 系统自动 RAG 检索 → 拼接上下文 → LLM/Agent 回答

两者区别可以这样说：

1
2

RAG 作为工具：Agent 主动调用，灵活，适合多步任务
RAG 作为内部模块：系统自动检索，稳定，适合标准问答

在 Coding Agent 里，我更倾向把 RAG 设计成工具或子模块混合使用。比如项目文档检索、历史记忆检索、代码片段检索都可以作为工具，由 Agent 在需要时调用。但对于某些固定场景，比如用户明确问知识库问题，可以默认先走 RAG pipeline。

最后可以总结一句：RAG 解决的是“从外部知识中找证据”，Agent 解决的是“决定下一步做什么”。当二者结合时，RAG 可以成为 Agent 的一个知识工具，也可以成为系统默认的上下文增强模块。选择哪种方式取决于任务是否需要多步决策。

41. Llama 类模型和原始 Transformer 的主要区别

原始 Transformer 是 encoder-decoder 架构，最早用于机器翻译。它包含 encoder 和 decoder 两部分。Encoder 负责理解输入句子，decoder 负责一步一步生成输出句子。

Llama 类大语言模型一般是 decoder-only Transformer。它没有 encoder，只有一层层 decoder block。它的任务是根据前面的 token 预测下一个 token。

原始 Transformer 的典型结构是：

1

输入句子 → Encoder → Decoder → 输出句子

Llama 类模型的结构是：

1

token 输入 → embedding → 多层 decoder block → lm_head → 预测下一个 token

主要区别有几个。

第一，架构不同。原始 Transformer 是 encoder-decoder，Llama 是 decoder-only。

第二，注意力方式不同。原始 Transformer 的 encoder 用双向 attention，可以看完整输入；decoder 用 causal attention，只能看当前位置之前的 token。Llama 全部使用 causal self-attention，因为它是自回归生成模型。

第三，归一化不同。原始 Transformer 常用 LayerNorm，Llama 常用 RMSNorm。

第四，位置编码不同。原始 Transformer 用绝对位置编码，Llama 常用 RoPE 旋转位置编码。

第五，FFN 不同。原始 Transformer 常用普通 FFN，比如：

1

Linear → ReLU/GELU → Linear

Llama 常用 SwiGLU：

1

Linear1(x) * SiLU(Linear2(x)) → Linear3

第六，推理优化不同。Llama 这类自回归模型通常会实现 KV Cache，用来加速逐 token 生成。

面试可以这样总结：

Llama 本质上是 decoder-only Transformer。相比原始 Transformer，它去掉了 encoder，只做自回归预测；使用 causal attention、RoPE、RMSNorm、SwiGLU，并在推理阶段使用 KV Cache 提高生成效率。

42. RMSNorm 和 LayerNorm 有什么区别？为什么 Llama 常用 RMSNorm？

LayerNorm 的作用是对 hidden state 做归一化，让训练更稳定。

LayerNorm 会减均值、除标准差：

1

LayerNorm(x) = (x - mean(x)) / sqrt(var(x) + eps) * gamma + beta

也就是说，LayerNorm 同时使用均值和方差。

RMSNorm 只除以均方根，不减均值：

1

RMSNorm(x) = x / sqrt(mean(x²) + eps) * gamma

它只关心向量的整体尺度，不关心均值平移。

区别很简单：

1
2

LayerNorm：减均值 + 除标准差
RMSNorm：不减均值，只除 RMS

RMSNorm 的优点是计算更简单，少算 mean-centering，速度更快，参数也更少。大模型里每一层都要做归一化，层数很多，所以这点优化会带来实际收益。

Llama 常用 RMSNorm 的原因是：它在大模型训练中足够稳定，同时比 LayerNorm 更轻量，推理和训练效率更好。

面试可以这样说：

RMSNorm 可以理解成 LayerNorm 的简化版本。LayerNorm 同时归一化均值和方差，RMSNorm 只归一化向量尺度。Llama 使用 RMSNorm，是因为它计算更便宜，同时在大模型中仍然能保持训练稳定。

43. SwiGLU 相比普通 FFN 的优势是什么？公式是什么？

普通 Transformer 的 FFN 一般是：

1

FFN(x) = W2 * activation(W1 * x)

比如：

1

Linear → ReLU/GELU → Linear

SwiGLU 是一种带门控的前馈网络。它不是只做一次非线性变换，而是引入一个 gate。

常见公式是：

1

SwiGLU(x) = W3( SiLU(W1x) ⊙ W2x )

其中：

1

SiLU(z) = z * sigmoid(z)

⊙ 表示逐元素相乘。

可以拆开理解：

1
2
3
4

a = W1x
b = W2x
gate = SiLU(a)
output = W3(gate * b)

普通 FFN 是直接变换，SwiGLU 多了一个门控机制。门控的作用是让模型自己决定哪些维度的信息应该通过，哪些应该抑制。

优势是：表达能力更强，非线性更灵活，训练效果通常更好。很多现代大模型，比如 Llama、PaLM 系列，都使用 GLU 变体。

面试可以这样说：

SwiGLU 相比普通 FFN，多了一个 gate。它用 SiLU(W1x) 控制 W2x 中哪些信息通过。这样模型的特征选择能力更强，通常比普通 ReLU/GELU FFN 表达能力更好。

44. RoPE 的核心思想是什么？为什么更适合长文本外推？

RoPE 是 Rotary Position Embedding，旋转位置编码。

普通绝对位置编码是给每个位置加一个位置向量：

1

x_i = token_embedding_i + position_embedding_i

RoPE 不是简单相加，而是把位置信息通过“旋转”作用到 Q 和 K 上。也就是说，每个 token 的 Q、K 向量会根据它的位置做一个旋转变换。

简单理解：

1

位置越靠后，Q/K 被旋转的角度越大

这样 attention 计算时：

1

Q_i · K_j

不仅包含 token 内容信息，也包含位置 i 和位置 j 的相对关系。

RoPE 的核心优点是：它天然把相对位置信息编码进 attention 分数里。模型不只是知道“这是第几个 token”，还更容易知道“两个 token 相隔多远”。

为什么适合长文本外推？

因为绝对位置编码通常对训练长度依赖强。如果训练时最多见过 2048 位置，推理时扩到 8192，绝对位置 embedding 可能没有学过这些位置。

RoPE 用的是连续的旋转函数，不是单独给每个位置学一个 embedding。位置变化是规律性的，所以在超过训练长度时更容易外推。

面试可以这样说：

RoPE 的本质是对 Q 和 K 做位置相关的旋转，使 attention 分数包含相对位置信息。相比绝对位置编码，它不是为每个位置学习一个独立向量，而是用连续的旋转规律表示位置，所以对长文本外推更友好。

45. 多头注意力的计算过程，包括 Q、K、V 的 shape 变化

假设输入 hidden state 是：

1

x: [batch_size, seq_len, hidden_size]

比如：

1
2
3
4
5

batch_size = B
seq_len = T
hidden_size = D
num_heads = H
head_dim = D / H

第一步，对 x 做三组线性变换，得到 Q、K、V：

1
2
3

Q = x Wq
K = x Wk
V = x Wv

shape 是：

1
2
3

Q: [B, T, D]
K: [B, T, D]
V: [B, T, D]

第二步，把 hidden_size 拆成多个 head：

1
2
3

Q: [B, T, H, head_dim]
K: [B, T, H, head_dim]
V: [B, T, H, head_dim]

为了方便矩阵乘法，通常转置成：

1
2
3

Q: [B, H, T, head_dim]
K: [B, H, T, head_dim]
V: [B, H, T, head_dim]

第三步，计算 attention score：

1

score = Q @ K^T / sqrt(head_dim)

shape 变化：

1
2
3

Q:        [B, H, T, head_dim]
K^T:      [B, H, head_dim, T]
score:    [B, H, T, T]

score[b, h, i, j] 表示第 b 个样本、第 h 个头里，第 i 个 token 对第 j 个 token 的注意力分数。

第四步，加 mask。自回归模型要用 causal mask，防止当前位置看到未来 token。

比如第 5 个 token 只能看 1 到 5，不能看 6、7、8。

第五步，softmax：

1

attn = softmax(score)

shape 还是：

1

attn: [B, H, T, T]

第六步，用 attention 权重加权 V：

1

out = attn @ V

shape：

1
2
3

attn: [B, H, T, T]
V:    [B, H, T, head_dim]
out:  [B, H, T, head_dim]

第七步，把多个 head 拼回去：

1

out: [B, T, H, head_dim] → [B, T, D]

第八步，过输出线性层：

1

output = out Wo

shape：

1

output: [B, T, D]

面试时可以按这个流程说：

1

x → Q/K/V 线性映射 → 拆多头 → QK^T 算注意力分数 → 加 causal mask → softmax → 乘 V → 拼接多头 → 输出线性层

46. 自回归解码为什么需要 KV Cache？没有 KV Cache 复杂度是什么？优化在哪里？

自回归解码是一个 token 一个 token 生成。

比如已经生成：

1

我 今天 想

模型下一步预测：

1

吃

再下一步输入变成：

1

我 今天 想 吃

如果没有 KV Cache，每生成一个新 token，模型都要重新计算前面所有 token 的 K 和 V。

例如生成第 t 个 token 时，要重新计算长度为 t 的整个序列：

1
2
3
4
5

第 1 步：算 1 个 token
第 2 步：重新算 2 个 token
第 3 步：重新算 3 个 token
...
第 T 步：重新算 T 个 token

总计算量大约是：

1

1 + 2 + 3 + ... + T = O(T²)

而且每层都要重复算历史 token 的 K、V。

KV Cache 的做法是：历史 token 的 K、V 算过之后就缓存起来。下一步生成新 token 时，只需要计算新 token 的 Q、K、V，然后把新 K、V 追加到 cache 里。

没有 KV Cache：

1

每一步都重新算全部历史 K/V

有 KV Cache：

1

历史 K/V 直接复用，只算新 token 的 K/V

优化点在于：减少重复计算。生成第 t 个 token 时，不再重新计算前 t-1 个 token 的 K、V。

但是注意：当前 token 的 Q 还是要和所有历史 K 做 attention，所以 attention 仍然要看历史长度。KV Cache 主要节省的是历史 K/V 的重复投影计算。

面试可以这样说：

KV Cache 是自回归推理的缓存机制。没有它，每生成一个 token 都要重新计算整个前缀的 K/V，重复计算很多。有了 KV Cache，历史 K/V 只算一次，后面直接复用，所以生成速度大幅提升。

47. KV Cache 的代价是什么？显存占用和 batch、seq length、layer number、hidden size 的关系？

KV Cache 的代价是占显存。

因为每一层都要保存历史 token 的 K 和 V。保存的内容包括：

1
2

K cache
V cache

每层都有一份。

KV Cache 显存大致和这些量成正比：

1
2
3
4
5
6
7

batch_size
seq_len
num_layers
num_heads
head_dim
2   # K 和 V 两份
dtype_size

公式可以写成：

1

KV Cache memory ≈ 2 × B × T × L × H × head_dim × dtype_size

因为：

1

H × head_dim = hidden_size

所以也可以写成：

1

KV Cache memory ≈ 2 × B × T × L × hidden_size × dtype_size

其中：

1
2
3
4
5

B = batch size
T = sequence length
L = layer number
hidden_size = 模型隐藏维度
dtype_size = 每个数占多少字节

如果是 FP16 或 BF16：

1

dtype_size = 2 bytes

如果是 FP32：

1

dtype_size = 4 bytes

所以 batch 越大，显存线性增加；seq length 越长，显存线性增加；层数越多，显存线性增加；hidden size 越大，显存线性增加。

举个简单例子：

1
2
3
4

batch 越大 → 同时缓存更多样本的 KV
seq_len 越长 → 每个样本历史 token 更多
layer 越多 → 每层都要存一份 KV
hidden_size 越大 → 每个 token 的 K/V 向量更大

KV Cache 解决了速度问题，但带来了显存问题。长上下文推理时，显存瓶颈往往不是参数，而是 KV Cache。

面试可以这样说：

KV Cache 用显存换速度。它缓存每层、每个历史 token 的 K 和 V，所以显存和 batch size、序列长度、层数、hidden size 都近似线性相关。长上下文和大 batch 下，KV Cache 会成为主要显存开销。

48. BPE 分词是什么？和 WordPiece、SentencePiece 有什么区别？

BPE 是 Byte Pair Encoding，字节对编码。它的思想是：从最小单位开始，不断把高频相邻符号合并成新的 token。

简单流程：

先把文本拆成很小的单位，比如字符或 byte。

例如：

1

low lower lowest

初始可以拆成：

1
2
3

l o w
l o w e r
l o w e s t

然后统计相邻符号对的频率。比如 l + o 经常一起出现，就合并成 lo。接着 lo + w 经常出现，就合并成 low。不断重复，直到词表大小达到目标。

BPE 的结果是：常见词可能作为完整 token，不常见词会被拆成子词。

例如：

1

unbelievable → un + believe + able

这样可以解决 OOV，也就是词表外单词问题。模型不用为每个单词都准备一个独立 token。

WordPiece 和 BPE 很像，也做子词合并。区别是 WordPiece 合并时更偏向最大化语言模型似然，不是单纯按频率合并。BPE 通常按频率合并，WordPiece 更看合并后对语料概率的提升。

SentencePiece 是一个分词工具/框架，不依赖空格预分词。它可以直接把句子当成原始字符序列处理，适合中文、日文这类没有天然空格分词的语言。SentencePiece 里面可以实现 BPE，也可以实现 Unigram。

简单对比：

1
2
3

BPE：按高频相邻符号对合并，简单直接
WordPiece：也做子词，但合并标准更偏概率建模
SentencePiece：分词框架，不依赖空格，可使用 BPE 或 Unigram

面试可以这样说：

BPE 是一种子词分词算法，从字符或 byte 开始，不断合并高频相邻符号，最后形成词表。它能把低频词拆成子词，减少 OOV。WordPiece 和它类似，但合并标准不同。SentencePiece 更像一个通用分词框架，可以在无空格语言上直接训练，并支持 BPE 或 Unigram。

49. CUDA 算力对齐具体做了什么？

这个问题里“CUDA 算力对齐”容易说虚。面试时要说具体操作，不能只说“用了 GPU”。

可以从四个层面回答。

第一，设备对齐。也就是保证模型参数、输入 tensor、mask、position ids 都在同一个 device 上。

常见错误是：

1

Expected all tensors to be on the same device, but found cuda:0 and cpu

所以要做：

1
2
3

model = model.to(device)
input_ids = input_ids.to(device)
attention_mask = attention_mask.to(device)

第二，数据类型对齐。训练或推理时，要控制 FP32、FP16、BF16。大模型通常不会全用 FP32，因为太占显存、速度慢。可以用：

1

FP16 / BF16 mixed precision

这样能减少显存占用，提高 GPU 吞吐。

第三，shape 对齐。注意力里 Q、K、V 的 shape 必须适合矩阵乘法。比如：

1
2

Q: [B, H, T, D_head]
K: [B, H, T, D_head]

计算时要转置 K：

1

Q @ K.transpose(-2, -1)

如果 shape 不对，就会报维度错误，或者性能很差。

第四，KV Cache 的显存管理。推理时要提前分配或维护 cache，避免每一步频繁创建大 tensor。生成时把新的 K/V 写入缓存，而不是每次重复 concat 大量历史内容。频繁 concat 会造成显存碎片和速度下降。

第五，算子和 batch 优化。比如尽量使用矩阵乘法而不是 Python for-loop；尽量让 batch 维度参与并行；注意 mask 的 shape 广播；在可能的情况下使用 PyTorch 的 fused scaled dot product attention。

所以如果面试官问“你具体做了什么”，可以这样说：

我做的 CUDA 对齐主要包括：保证模型、输入、mask、KV Cache 都在同一张 GPU 上；使用 FP16/BF16 降低显存；检查 Q/K/V 的 shape，使 attention 计算能走高效矩阵乘法；在自回归推理中维护 KV Cache，避免重复计算和频繁拷贝；同时避免 CPU/GPU 来回搬运数据。

不要只说：

1

我把模型放到 GPU 上

要说：

1

device 对齐、dtype 对齐、shape 对齐、cache 管理、减少 CPU-GPU 数据拷贝

class SearchCodeTool(Tool):

    def run(self, query, root="."):

class ToolRegistry:
    def __init__(self):
        self.tools = {}

    def register(self, tool):
        self.tools[tool.name] = tool

    def execute(self, tool_name, arguments):
        tool = self.tools[tool_name]
        return tool.run(**arguments)


class Agent:
    def __init__(self, llm, tool_registry, max_steps=10):
        self.llm = llm
        self.tool_registry = tool_registry
        self.max_steps = max_steps

    def run(self, user_query):
        state = AgentState(user_query)

        for step in range(self.max_steps):
            prompt = self.build_prompt(state)
            action = self.llm.generate_action(prompt)

            if action["type"] == "final":
                state.done = True
                state.final_answer = action["content"]
                break

            if action["type"] == "tool_call":
                tool_name = action["tool"]
                arguments = action["arguments"]

                try:
                    observation = self.tool_registry.execute(tool_name, arguments)
                except Exception as e:
                    observation = {"error": str(e)}

                state.steps.append(action)
                state.observations.append(observation)

        return state.final_answer or self.summarize(state)

    def build_prompt(self, state):
        return {
            "user_query": state.user_query,
            "history": state.steps,
            "observations": state.observations,
            "tools": list(self.tool_registry.tools.keys())
        }

56. Claude Code 这类 Coding Agent 的关键壁垒是什么？

这个问题不能只说“模型能力”。模型能力当然重要，但 Coding Agent 的壁垒更多是系统工程。

可以这样回答：

Claude Code 这类 Coding Agent 的关键壁垒不是单一模型能力，而是模型能力、工具系统、上下文管理、代码环境理解、执行反馈、安全控制和工程细节的组合。

模型能力决定 Agent 能不能理解代码、规划任务、分析错误、生成正确 patch。但如果只有模型，没有工具，它就只能凭空回答，不能真实读取仓库、运行测试、查看 diff。

工具系统是第二个壁垒。Coding Agent 必须能稳定调用读文件、搜索代码、运行命令、编辑文件、查看 git diff、执行测试等工具。工具 schema 要清楚，错误返回要结构化，权限要可控。

上下文管理是第三个壁垒。真实代码仓库很大，测试日志也很长，不可能全部塞进 prompt。Agent 必须知道读什么、不读什么、如何摘要、如何恢复细节、如何保持长任务状态。

执行反馈是第四个壁垒。好的 Coding Agent 不是一次生成代码，而是修改后运行测试，根据失败日志继续修正。这个闭环比单次代码生成更关键。

安全控制是第五个壁垒。Agent 能执行命令和改文件，就必须限制路径、限制危险命令、保护隐私文件、保留 diff 和回滚能力。

工程细节是最后的壁垒。比如如何避免死循环、如何处理依赖缺失、如何做 patch 合并、如何记录日志、如何恢复失败任务、如何管理多 Agent 并发。这些不是模型本身能自动解决的。

可以总结成一句：

Claude Code 的壁垒不是“会写代码”这么简单，而是把模型、工具、上下文、测试反馈、权限安全和工程状态管理组合成一个稳定闭环。

58. Agent 修改代码引入 bug，怎么发现？有没有 test generation、static analysis、lint、rollback？

这个问题要回答成完整防线。

可以这样回答：

Agent 修改代码后，不能只看模型自己说“修好了”，必须通过验证机制发现是否引入 bug。我会设计几层检查。

第一层是 diff 检查。修改后先查看 git diff，确认改了哪些文件、哪些函数、修改范围是否符合任务。如果用户只是要求修一个函数，但 Agent 改了十几个无关文件，就要拦截。

第二层是静态检查。比如 Python 可以运行 ruff、flake8、mypy、pyright，前端可以运行 eslint、tsc。静态检查可以发现语法错误、类型错误、未使用变量、导入错误等。

第三层是单元测试。优先运行和修改文件相关的目标测试，而不是一上来跑全量测试。比如修改了 auth.py，先跑 tests/test_auth.py。如果目标测试通过，再根据成本决定是否跑更大范围测试。

第四层是 test generation。如果项目缺少测试，可以让 Agent 根据修改逻辑生成最小测试用例。比如修复 token 过期逻辑，就生成一个 expired token 的测试。生成测试后也要运行，不能只生成文件。

第五层是回归测试。如果修改影响公共函数或核心模块，需要跑相关模块测试，防止修了 A 坏了 B。

第六层是 rollback。每次修改前保存 patch 或依赖 git 状态。如果测试失败且无法修复，系统可以撤销这次修改，回到修改前状态。

第七层是人工确认。对于大范围重构、删除代码、修改配置文件、改测试预期这类高风险操作，不应该自动提交，应该给用户 diff 和风险说明。

可以总结成流程：

1

修改代码 → 查看 diff → 静态检查 → 目标测试 → 必要时生成测试 → 回归测试 → 失败则修正或 rollback → 输出验证结果

面试时要强调：Agent 写代码不是最终目标，能验证代码才是关键。没有测试和回滚的 Coding Agent 很危险。

我会把日志分成任务级日志、步骤级日志、工具级日志、模型输入输出摘要、代码修改日志和评估日志。

任务级日志记录用户原始请求、任务 ID、项目 ID、开始时间、结束时间、最终状态、是否成功、失败原因。

步骤级日志记录每一轮 Agent Loop 的状态。比如当前计划是什么，模型决定调用什么工具，为什么进入下一步，是否触发 retry 或 reflection。

工具级日志记录工具调用详情。包括工具名、参数、权限检查结果、执行状态、stdout、stderr、exit code、耗时、是否失败。比如 run_command 失败，要记录命令、工作目录、错误输出。

模型日志不一定保存完整 prompt，因为可能很长或包含敏感信息，但至少要保存 prompt 摘要、使用的上下文引用、模型输出的 action、解析是否成功。如果工具调用 JSON 格式错了，也要记录。

代码修改日志记录修改前后的 diff、修改文件、修改行号、是否通过测试、是否回滚。这个很关键，因为失败任务经常要看 Agent 到底改了什么。

安全日志记录哪些操作被拦截，比如访问 .env、执行 rm -rf、越界路径、sudo 命令等。

60. 如果把 MiniCode 部署成多人使用的服务，还要考虑哪些工程问题？

从个人原型到多人服务，问题会复杂很多。不能只考虑 Agent 能不能跑，还要考虑用户隔离、权限、安全、并发、成本、可靠性和监控。

首先是用户隔离。每个用户的代码仓库、文件、记忆、日志、API key 都必须隔离。不能出现 A 用户的代码被 B 用户检索到，也不能共享隐私记忆。

其次是沙箱环境。Agent 会运行命令和修改文件，必须放在容器或隔离环境里。每个任务最好有独立 workspace，限制 CPU、内存、磁盘、网络和执行时间。不能让用户代码影响宿主机。

第三是权限系统。读文件、写文件、运行命令、安装依赖、访问网络、删除文件都要分权限。高风险操作需要用户确认。

第四是并发调度。多人同时使用时，要有任务队列、worker、超时控制、失败重试和资源限制。否则一个长任务会拖垮系统。

第五是状态管理。Agent 任务可能运行很久，中途失败或用户刷新页面后要能恢复。所以需要保存任务状态、工具结果、上下文引用、diff 和日志。

第六是成本控制。LLM 调用、embedding、rerank、长上下文都会花钱。需要限制最大轮数、最大 token、最大工具调用次数，并做缓存。

第七是代码安全。用户仓库可能包含恶意脚本，Agent 运行测试时可能执行不安全代码。所以默认要限制网络，限制系统权限，避免执行危险命令。

第八是数据隐私。日志和 prompt 里可能包含代码、密钥、业务逻辑。要做脱敏、访问控制、加密存储、日志保留期限管理。

第九是版本控制和回滚。多人服务必须让用户看到 Agent 做了哪些修改，可以查看 diff，可以接受或拒绝，可以一键回滚。

第十是监控和评估。要监控任务成功率、平均耗时、错误率、token 成本、工具失败率、用户取消率、安全拦截次数。

第十一是记忆管理。多人系统中记忆必须按用户、项目、组织隔离。还要支持用户删除记忆、关闭记忆、查看记忆来源。

第十二是 API 和前端体验。用户需要看到 Agent 当前在做什么，比如正在搜索文件、正在运行测试、正在修改代码，而不是黑盒等待。

可以总结成一句：

单人原型关注 Agent 能不能完成任务；多人服务还要解决隔离、安全、并发、状态恢复、成本控制、监控、权限和隐私问题。真正难点会从模型逻辑扩展到完整工程系统。

61. 设计一个 Agent：用户上传 Python 项目，要求自动修复 bug

这个 Agent 的完整流程可以分成八步。

第一步，接收项目并建立工作区。用户上传 Python 项目后，系统先把项目解压到一个隔离 workspace 中，不能直接在用户原文件上操作。然后记录项目路径、文件列表、是否有 requirements.txt、pyproject.toml、setup.py、pytest.ini 等配置文件。

第二步，分析项目结构。Agent 先读取目录结构，判断这是普通 Python 包、FastAPI 项目、机器学习项目，还是脚本项目。它会重点找入口文件、源码目录、测试目录和依赖配置。比如：

1
2
3
4

src/
tests/
requirements.txt
pyproject.toml

第三步，复现 bug。如果用户提供了报错日志，Agent 先解析日志，提取异常类型、报错文件、行号、失败测试名。如果用户没有提供日志，Agent 会尝试运行测试，例如：

1

pytest

或者先查看项目配置，判断正确测试命令。复现 bug 很关键，因为没有复现就直接修，容易瞎改。

第四步，定位 bug。Agent 根据报错信息搜索相关代码。比如报错是：

1

AttributeError: 'NoneType' object has no attribute 'xxx'

Agent 会找到对应文件和函数，读取相关源码、调用方和测试文件。定位时优先读小范围代码，不是一上来把整个项目塞进上下文。

第五步，分析原因。Agent 判断 bug 类型。常见类型包括：参数为空、路径错误、导入错误、依赖缺失、边界条件漏处理、类型不匹配、shape 不一致、配置错误、测试预期和业务逻辑不一致。分析时要区分“代码真的错了”还是“环境没配好”。

第六步，生成最小修改。Agent 不应该大范围重构，而是优先做最小 patch。比如只改一个条件判断、补一个空值检查、修一个 import 路径、改一个函数返回值。修改前最好记录 diff，方便回滚。

第七步，运行验证。修改后先运行目标测试，比如：

1

pytest tests/test_xxx.py::test_yyy

目标测试通过后，再根据成本运行相关模块测试或全量测试。验证不通过时，Agent 继续读取失败日志，进入下一轮修复。如果连续失败，就回滚或请求用户确认。

第八步，生成报告。最终报告要包括：bug 原因、修改文件、修改内容、测试命令、测试结果、是否还有风险。比如：

1
2
3
4
5

问题原因：token 过期判断条件错误。
修改文件：src/auth.py

验证：pytest tests/test_auth.py 通过
风险：未运行全量测试

可以总结成一句面试回答：

我会把自动修复 bug 设计成“建立沙箱 → 分析结构 → 复现 bug → 定位代码 → 分析原因 → 最小修改 → 测试验证 → 输出报告”的闭环，而不是让模型直接生成一段修复代码。

65. 如何区分 planning error、retrieval error、tool error、execution error？

这四类错误发生在 Agent 流程的不同位置。

planning error 是计划错了。Agent 对任务理解错，或者步骤安排错。

例子：

1
2

用户要修复测试失败，Agent 却开始重构项目结构。
用户只要求分析原因，Agent 却直接修改代码。

判断标准是：工具可能没错，检索也可能没错，但 Agent 一开始方向就偏了。

修复方式是重新理解用户目标，重新规划，必要时请求用户确认。

retrieval error 是找错资料或漏找资料。

例子：

1
2

用户问 auth.py 的 bug，系统召回了 README。
正确代码在 tests/test_auth.py，但没有检索到。

判断标准是：问题需要某些上下文，但系统没有找到，或者找到的是无关内容。

修复方式是改 query、扩大 top-k、换 embedding、加 keyword search、调整 metadata filter、做 rerank。

tool error 是工具调用本身失败。

例子：

1
2
3
4

read_file 路径不存在
run_command 命令格式错误
edit_file 参数不符合 schema
权限不足

判断标准是：Agent 想做的动作可能合理，但工具没有成功执行。

修复方式是根据错误信息 retry，比如路径不存在就先 list_dir，权限不足就请求确认，命令不存在就查项目配置。

execution error 是工具执行成功了，但结果没达到目标。

例子：

1
2
3

代码修改成功写入，但测试仍然失败。
测试命令成功运行，但暴露出新的失败。
patch 应用成功，但引入了回归 bug。

判断标准是：工具本身没报错，但任务结果失败。

修复方式是分析执行反馈，继续 debug，或者回滚修改。

简单区分：

1
2
3
4

planning error：想错了
retrieval error：找错了

66. 模型能力较弱，比如 7B 模型，如何通过系统设计提升 Agent 表现？

7B 模型能力弱，不能完全靠它自由规划。系统设计要帮它减少难度。

第一，减少模型选择空间。不要一次给它几十个工具。先用规则或路由选择相关 Skill，只暴露少量工具。比如修 bug 时只给：

第二，把复杂任务拆成小步骤。不要让 7B 一次完成“理解项目、定位 bug、修复、测试、总结”。应该拆成：

第四，加强规则控制。比如路径检查、权限检查、错误分类、retry 策略、测试命令选择，不要都交给模型。

第五，引入检索和模板。弱模型不擅长从零规划，可以给它 Skill 模板。比如 pytest debug 模板：

第六，使用 reranker 或较强模型做关键判断。如果预算允许，可以让 7B 做执行，让强模型做规划或最终 review。也可以让规则做初筛，LLM 只做语义判断。

第七，限制上下文长度和噪声。弱模型更容易被长上下文干扰，所以要做上下文压缩，只给它必要信息。

第八，增加验证闭环。弱模型可能生成错误代码，所以必须依赖测试、lint、static analysis、diff review 来纠错。

一句话总结：

弱模型不要让它“自由 Agent 化”。要用路由、模板、规则、结构化输出、工具反馈、测试验证和上下文压缩，把复杂任务拆成它能处理的小决策。

68. 未来 Coding Agent 的核心研究问题是什么？

未来 Coding Agent 的核心问题不是“能不能生成代码”，而是“能不能可靠地完成真实软件工程任务”。

主要研究问题有几个。

第一，长上下文代码理解。真实项目有很多文件、依赖、配置和历史提交。Agent 要知道读哪些文件、忽略哪些文件、如何理解跨文件调用关系。

第二，可靠任务规划。复杂任务不能一步完成，Agent 要能拆解、排序、调整计划，并在失败时重新规划。

第三，工具使用稳定性。Agent 要能正确调用搜索、读取、编辑、测试、git、CI 等工具，并处理工具失败。

第四，代码修改的正确性验证。生成 patch 很容易，难的是确认 patch 没有引入新 bug。未来需要更强的测试生成、静态分析、语义验证和回归检测。

第五，记忆和经验复用。Agent 要能记住项目结构、用户偏好、历史 bug、常用命令，但又不能被错误记忆污染。

第六，安全和权限控制。Coding Agent 能读写文件、执行命令，所以必须防止越权访问、删除文件、泄露密钥和 prompt injection。

第七，多 Agent 协作。未来复杂任务可能需要多个 Agent 分工，但核心问题是如何分工、合并结果、处理冲突，而不是简单堆多个 Agent。

第八，评估体系。现在很多评估只看代码题，但真实 Coding Agent 还要评估工具调用、长任务成功率、成本、回滚、安全和用户交互。

一句话总结：

未来 Coding Agent 的核心研究问题是：如何让模型在真实代码仓库中，安全、可验证、低成本地完成多步软件工程任务。

69. 做一个 Agent 论文实验，baseline 和 evaluation 怎么设计？

如果要做 Agent 论文实验，首先要明确研究点。比如你研究的是 Skill 路由、记忆系统、上下文压缩，还是多 Agent 协作。不同研究点 baseline 不一样。

假设研究对象是 MiniCode 这种 Coding Agent，可以设计几个 baseline。

第一个 baseline 是普通 LLM。不给工具，只把问题和部分代码塞给模型，看它能不能回答或修复。

第二个 baseline 是 ReAct Agent。给模型工具调用能力，但不加 Skill 路由、不加记忆、不加上下文压缩。

第三个 baseline 是 Tool Agent。只做基础工具调用和测试执行，没有高级规划和记忆。

第四个 baseline 是 RAG Agent。加入代码检索，但不加入长期记忆和 Skill 路由。

第五个 baseline 是完整 MiniCode。包括 Skill 路由、上下文压缩、记忆系统、权限控制和测试反馈。
