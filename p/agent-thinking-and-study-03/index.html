啥是RAG？

先翻译一下，Retrieval Augmented Generation ,检索增强生成。

类似于搜索引擎，找到用户提问最相关的知识或者是相关的对话历史，并结合原始提问，创造信息丰富的prompt，指导模型生成准确输出。

本质应用了上下文学习的原理，RAG = 检索技术+大模型提示。

他解决的了大模型的一些问题，比如：大模型容易“一本正经地胡说八道”，RAG通过引入外部真实信息进行事实核查，大幅减少幻觉。大模型的知识停留在训练切断时间，RAG可以通过外挂知识库实时获取最新数据。企业直接微调模型容易泄露敏感数据，RAG可以在检索阶段设置权限控制，保障本地数据安全。提高了回答的准确性与可靠性；便于极低成本地更新和扩展外部知识（无需重新训练模型）；提供数据隐私保护；缓解了对大模型庞大参数和巨大计算资源的依赖。

RAG流程与分类

可以分为四个基本流程：

1、知识文档的准备：

就是前置数据处理，我们面对的知识源可能包含多种格式，比如word，txt，csv等等，因此第一步需要使用专门的文档加载器将丰富的 知识源转换为大语言模型可理解的纯文本数据。此外，对于文档可能存在过长的问题，我们还需要进行切片，将长篇文档分割成多个文本块，以便于高效处理信息。

2、Embedding向量化：

将文本块和用户的查询（Query）通过Embedding模型转化为多维向量，存入向量数据库。

3、数据库检索：

计算用户查询向量与数据库中文档向量的相似度，召回最相关的Top-K个文档块。

4、答案生成：

将检索到的背景上下文信息与用户的原始问题进行拼接，输入给LLM生成最终答案。

主要分为三类，也是不断演化的结果

1、Naive RAG（朴素RAG）：最基础的范式，直接按“索引-检索-生成”的线性流程进行。缺点是检索的准确率和召回率受限，容易出现上下文不够相关导致生成质量不高。

2、Advanced RAG（高级RAG）：针对朴素RAG进行了优化，增加了检索前（Pre-Retrieval）（如查询重写、扩展）和检索后（Post-Retrieval）（如结果重排 Rerank、上下文压缩）处理模块。有效缓解了LLM常见的“Lost in the Middle”（遗忘中间信息）现象，提升了检索质量。

3、Modular RAG（模块化RAG）：这是目前最先进、灵活的架构。它将整个过程模块化（如引入搜索模块、路由模块、记忆模块等），允许根据实际场景自由组合、替换或重排各个模块，不再局限于单一的线性流程。

RAG评估

通过上面的论述，我们发现rag包含检索和生成。我们需要对其进行系统化评估。

当 RAG 系统给出一个糟糕的回答时，评估可以帮助我们定位问题出在哪里。是检索器（Retriever）没有找到相关的背景文档？还是生成器（LLM）理解错了文档、产生了幻觉，或者答非所问？ RAG 系统中有大量的超参数和组件（如 Chunk Size 分块大小、Embedding 模型选择、Top-K 数量、是否加入 Reranker、Prompt 的设计、选择哪个 LLM 等）。只有建立定量的评估指标，才能科学地对比不同策略的效果，指导后续的系统迭代。并且确保模型回答的“忠实度”（没有脱离知识库胡编乱造），这对于企业级应用（如医疗、法律客服）至关重要。

针对检索环节的评估

在构建 RAG（检索增强生成）系统时，整个流水线通常被划分为两部分：检索器和生成器。

如果在生成阶段，大模型输出了幻觉或答非所问的内容，问题常常并不出在模型本身，而是因为检索器喂给大模型的“参考资料”质量太差。所谓“Garbage in, Garbage out（垃圾进，垃圾出）”。

因此，针对检索环节的独立评估至关重要。它的核心目的就是回答一个问题：从庞大知识库中召回的 Top-K 个文档块（Chunks），究竟准不准、全不全、排序好不好？

我们将这几个核心指标拆解为三个递进的层次：找没找到（Hit Rate/Recall） -> 第一个找到的有多快（MRR） -> 整体排序质量有多好（NDCG）。

第一层：基础的“找没找到” (Hit Rate / Precision / Recall)

这是最基础的评估维度，只看检索出的文档集合里有没有我们要的内容，暂时不关心排名先后。

为了严谨定义这三个指标，我们需要先确立三个基础的数学集合参量。设针对某次特定的用户查询（Query）：

  • $R$ (Relevant)：知识库中所有真正相关的文档构成的集合。
  • $K$ (Retrieved)：系统经过检索，最终召回并输入给大模型的文档集合（通常为系统设定的 Top-K 阈值）。
  • $R \cap K$ (交集)：系统召回的文档中，确属相关的有效文档集合。

基于以上定义，该阶段主要涉及以下三个核心概念：

1. 精确率 (Precision) —— 衡量检索结果的纯净度

  • 逻辑定义：精确率计算的是在系统召回的 $K$ 个文档中，真正相关的文档所占的比例。

  • 数学表达：$Precision = \frac{|R \cap K|}{|K|}$

在 RAG 中的工程意义：精确率的高低直接决定了构建给大模型（LLM）的 Prompt 质量。精确率越低，意味着大模型的上下文中充斥着越多的无效“噪音”。这些无关信息不仅会大量占用有限的 Token 窗口上限，更容易干扰大模型自身的注意力机制（Attention Mechanism），使其偏离核心问题，从而大幅增加生成“幻觉（Hallucination）”的风险。

2. 召回率 (Recall) —— 衡量检索结果的完备性

  • 逻辑定义：召回率计算的是在知识库所有实际相关的 $R$ 个文档中，被系统成功检索出来并包含在 $K$ 中的比例。
  • 数学表达：$Recall = \frac{|R \cap K|}{|R|}$

在 RAG 中的工程意义：当面临复杂的、需要多跳推理（Multi-hop reasoning）或跨文档总结的问答任务时，召回率至关重要。如果召回率不足（例如回答问题需要综合 3 篇文档，系统只找出了 1 篇），意味着大模型缺失了生成完整答案的必要前置条件（即信息孤岛效应），这必然会导致最终输出的答案存在严重的片面性或关键信息遗漏。

3. 命中率 (Hit Rate) —— 衡量单次查询的底线有效性

  • 逻辑定义：与精确率和召回率关注连续的“比例”不同，命中率针对单次查询是一个二值化（Binary）的非黑即白指标。它不关心召回了多少篇相关文档，只判定检索结果集中是否至少包含一篇有效文档。
  • 数学表达：当 $|R \cap K| > 0$ 时，单次查询得分为 1；当 $|R \cap K| = 0$ 时，得分为 0。系统整体的命中率即为所有查询测试用例中得分为 1 的占比。

在 RAG 中的工程意义：命中率是 RAG 工业界最关注的实用基准指标。得益于现代大语言模型极强的阅读理解与信息抽取能力，系统往往不需要实现 100% 的召回率。只要在检索出的 Top-K 文档中，包含了哪怕一条正确的背景线索，大模型就足以推理出正确答案。因此，命中率衡量的是检索器是否跨过了保证 RAG 流水线“基本可用”的最低及格线。

第二层：首个正确答案的位置 (MRR - Mean Reciprocal Rank)

有时我们只关心最快找到的那一个正确答案。比如在问答系统（QA）中，只要第一条检索结果是完美的答案，后面的结果是好是坏其实无所谓。

MRR（平均倒数排名） 就是专门衡量这个的指标：

  1. RR (Reciprocal Rank，倒数排名): 针对单次查询。如果第一个相关的文档排在第 1 位，得分为 1/1 = 1。如果排在第 2 位，得分为 1/2 = 0.5。排在第 $n$ 位，得分就是 $1/n$。如果没有找到，得分为 0。
  2. MRR: 对多次查询的 RR 分数求平均值。
$$MRR = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{rank_i}$$
  • 查询 1：首个相关结果在第 2 位 $\rightarrow$ 分数 $1/2 = 0.5$
  • 查询 2：首个相关结果在第 5 位 $\rightarrow$ 分数 $1/5 = 0.2$
  • 查询 3：首个相关结果在第 1 位 $\rightarrow$ 分数 $1/1 = 1.0$
  • 平均结果 (MRR) = $\frac{1}{3} \times (0.5 + 0.2 + 1.0) = 0.567$

在算法层面上，这就好比遍历一个数组，MRR 只关心遇到的第一个 True 的索引位置，越靠前奖励越高，衰减非常快。

第三层：极其严苛的整体排序质量 (NDCG)

MRR 的局限在于它只看“第一个”正确结果。但很多时候，我们希望所有相关度高的文档都尽量排在前面。有些文档是“非常相关”，有些是“部分相关”，有些是“完全无关”。

NDCG（归一化折损累计增益） 是信息检索界最权威的指标之一，它不仅考虑了结果是否相关，还考虑了相关的程度以及它们所在的排位。

我们把它拆解开来看：

  1. CG (Cumulative Gain, 累计增益): 就是单纯把检索出的 Top-K 个文档的相关性得分（Rel）加起来。这不考虑位置，排第一和排最后得分一样。
  2. DCG (Discounted Cumulative Gain, 折损累计增益): 引入位置惩罚。排在后面的文档，即使相关性很高，其贡献值也要被打个折扣。
    • 公式：$DCG_k = \sum_{i=1}^{k} \frac{rel_i}{\log_2(i+1)}$
    • 解释： 分母 $\log_2(i+1)$ 就是“折损因子”。位置 $i$ 越大，分母越大，该文档的实际贡献得分就越小。
  3. IDCG (Ideal DCG, 理想折损累计增益): 假设系统是完美的，把所有文档按照相关性从高到低完美排序，此时计算出的 DCG 就是 IDCG（能拿到的理论最高分）。
  4. NDCG (Normalized DCG): 因为不同查询的难度不同（有的查询可能只有1个相关文档，有的有10个），直接对比 DCG 不公平。所以用当前的 $DCG$ 除以理论满分 $IDCG$，得到一个 0 到 1 之间的归一化分数。
    • 公式：$NDCG = \frac{DCG}{IDCG}$

作为研发人员，在优化 RAG 算法和数据结构时：

  • 如果你的 RAG 应用是事实类问答（答案唯一且明确），重点优化和关注 MRR。
  • 如果是分析总结类任务（需要多文档交叉验证），重点关注 Recall（召回率）。
  • 如果你在调试 Reranker（重排序模型）或者复杂的双塔 Embedding 模型，想要极致的排序效果，NDCG 是最综合、最科学的指标。

针对生成环节评估

生成环节的评估目标，是衡量 LLM 在接收到检索出的 Context（上下文）和用户的 Query（查询）后，最终输出的文本质量。这部分主要分为基于字面统计的量化评估和基于语义的非量化评估。

1. 量化评估：基于词法重合度的传统指标

  • 代表指标：ROUGE (Recall-Oriented Understudy for Gisting Evaluation)、BLEU (Bilingual Evaluation Understudy)。

这类指标的核心逻辑是计算 N-Gram（N元语法）的重合率。通过统计模型生成的文本与标准答案（Ground Truth）之间，有多少个词元（Token）或词组是完全相同的。

但是存在一些局限性，在现代 LLM 评估中，纯量化指标的权重正在急剧下降。因为大模型具备极强的同义词替换、句式重构和总结能力。即使生成的答案在字面上与参考答案毫无重合（导致 ROUGE/BLEU 分数极低），其在语义逻辑上依然可能是完全正确甚至更优的。

2. 非量化评估：基于多维度的语义指标

为了克服字面量化的缺陷，业界目前的主流方案是采用 LLM-as-a-Judge（大模型作为裁判） 范式，通过高维度的语义对齐来评估以下四个核心指标：

  • 完整性与正确性：生成的文本是否精准、无遗漏地回答了 Query 的核心诉求，且不存在事实性错误。
  • 上下文相关性：生成的回答是否强依赖于检索器提供的 Context。如果模型脱离了给定的上下文进行作答，即使答案是正确的，在该指标下也会被判定为低分。
  • 答案忠实性 (Faithfulness)：这是防范模型“幻觉（Hallucination）”的最关键防线。它严格审查最终答案中的每一个论点，是否都能在提供的 Context 中找到直接的证据支撑（Entailment）。禁止模型夹带其预训练权重中的未验证信息。
  • 答案相关性 (Answer Relevance)：衡量回答的精炼度与聚焦度。严厉惩罚大模型常见的“冗长废话”、“车轱辘话”或答非所问的现象。

意图分流评估

在 Agentic RAG 中，意图分流（Intent Routing）是整个数据链路的咽喉。Agent 需要通过 Function Call（工具调用）能力，决定是将问题抛给通用大模型，还是调用内部数据库 API、联网搜索工具等。

如果这一步的决策发生偏移，下游的所有生成都是无效的。图片中展示的是一个级联式的错误诊断模型，用于精确定位 Agent 在“感知 -> 规划 -> 执行”链路中的具体失效点。

设整个评估集中的总工具调用期望次数为 $N_{total}$。

1. 宏观指标：工具调用准确率

$$Accuracy = \frac{N_{success}}{N_{total}}$$

这是对 Agent 意图分流能力的整体评价，即最终成功调用正确工具并获取有效数据的比例。当该指标低于业务预期时，需要通过以下四个维度的“失败占比”进行归因拆解。

2. 感知层失效：工具意图识别失败占比

$$Rate_{intent\_fail} = \frac{N_{intent\_fail}}{N_{total}}$$

逻辑定义：Agent 未能从 Query 中识别出需要调用工具的意图（本该调用却没调用），或者在无需工具的场景下错误触发了工具。这通常意味着 Prompt 中对工具应用场景边界的定义（Description）存在歧义。

3. 路由层失效：工具名识别失败占比

$$Rate_{name\_fail} = \frac{N_{wrong\_name}}{N_{total}}$$

逻辑定义：Agent 成功识别了调用意图，但在可用的工具池（Tool Schema）中选错了具体的工具。例如，应该调用 search_arxiv_paper，却调用了 search_google_news。这说明工具池中的各项工具语义存在重叠，导致模型路由混乱。

4. 抽取层失效：工具参数识别失败占比

$$Rate_{param\_fail} = \frac{N_{correct\_name \cap wrong\_param}}{N_{total}}$$

逻辑定义：Agent 选对了正确的工具，但在依据工具 Schema 提取执行参数（Arguments）时发生了遗漏或类型错误。这是最常见的工程断点，通常需要通过增强大模型的 In-Context Learning（上下文学习）示例或约束 JSON 输出格式来解决。

5. 边界失控：工具幻觉识别失败占比

$$Rate_{hallucination} = \frac{N_{hallucinated\_tool}}{N_{total}}$$

逻辑定义：Agent 捏造并尝试调用了一个根本不在预设工具池中的工具名。这属于严重的安全性失效，表明模型的内部逻辑完全脱离了开发者设定的 Schema 约束。

答案评估

这是对大模型最终输出文本的基础质量把控，分为两个核心维度：

  1. 事实性评估 (Factuality) —— 核心目的是“防幻觉”
  • 逻辑原理：不再依赖单纯的字面比对，而是引入了一套自动化的事实核查流水线。

拆解流程：

  • 论点提取 (Claim Filtering)：首先把大模型生成的长篇大论拆解成一个个独立的“声明”或“论点”。
  • 证据检索 (Evidence Selection)：针对这些论点，去外部可信数据库（如 Wiki）或检索出的上下文中寻找证据。
  • 推理验证 (NLI 模型)：使用自然语言推理 (Natural Language Inference, NLI) 模型来判断关系。NLI 专门用于判断“前提”是否能推导出“假设”。如果生成的答案与检索出的事实存在“矛盾（Contradiction）”，则判定事实性不合格；如果存在“蕴含（Entailment）”关系，则事实性过关。
  1. 答案相关性 —— 核心目的是“防废话”
  • 逻辑原理：评估大模型的回答是否直接击中了用户的痛点，而不是长篇大论却不解决问题。
  • 演进方法：
    • 传统方法：计算生成的答案与人工标注的标准答案（Ground Truth）之间的余弦相似度等字面量化指标。
    • 现代方法 (LLM-as-a-Judge)：由于语言表达的多样性，现在更倾向于编写一套严格的 Prompt，让另一个能力更强的 LLM（如 GPT-4）来做裁判。裁判不仅比对答案与 Ground Truth 的语义一致性，还会直接结合用户的原始 Prompt，评估答案的切题程度。

噪音评估

在真实的 RAG 工程中，检索器是不完美的，常常会把含有大量关键词但实际上毫无用处的文档（即“噪音”）喂给大模型。

这是一项鲁棒性测试。系统故意向大模型输入“带有迷惑性的噪音文档”（例如：用户问“苹果公司2023年财报”，系统故意混入一篇“苹果种植技术”或“苹果公司2018年财报”的文档）。

  • 评估目标：考察大模型的注意力机制是否会被带偏。优秀的模型能够像人类一样，在阅读完所有资料后，自动屏蔽无效的噪音信息，精准提取出有用的片段进行总结，最终输出的答案能够与标准答案达成“精确匹配”。如果模型把噪音内容写进了答案，这项评估即为不合格。

分专项能力评估

在 RAG 的工程实践中，“分专项能力评估”属于对抗性测试。它们的评估原理，本质上是给大模型“挖坑”，然后观察并量化它的应对表现。

以下具体实操原理与逻辑链路（5种）：

  1. 易混淆实体评估
  • 测试目的：考察大模型是否具备实体隔离能力，防止出现“特征融合”的张冠李戴。
  • 如何构造测试（挖坑）： 向系统注入包含多重同名（或近义）实体的上下文。例如，用户查询：“苹果的最新营养研究和苹果的最新财报”。系统强制召回两篇文档，一篇是关于水果苹果的维基百科，另一篇是苹果公司的 Q3 财报。
  • 评估原理与打分机制：
    • LLM-as-a-Judge 审查：使用裁判大模型扫描生成的答案，检查是否存在逻辑谬误。如果模型回答出“苹果公司发布了含有 95 卡路里的 iPhone 15”，裁判模型会捕获到实体属性的交叉污染，该项得分为 0。
    • 通过标准：模型必须在回答中明确使用连接词（如“关于水果方面…而关于科技公司方面…”）将两者逻辑隔离，才能得分。
  1. 弱相关性与信息冲突评估
  • 测试目的：测试当检索库中存在“脏数据”或“矛盾数据”时，大模型的辨伪与择优能力。
  • 如何构造测试（挖坑）： 故意针对同一个客观事实，提供两篇相互矛盾的文档。例如，针对问题“地球是宇宙的中心吗？”，注入文档 A（地心说，错误事实）和文档 B（日心说，正确事实）。
  • 评估原理与打分机制：
    • 交叉验证率计算：评估大模型是否直接“盲信”了排在第一位的文档。
    • 择优逻辑检验：优秀的模型应当在输出中体现出置信度判断（例如：“虽然文档 A 称…但根据文档 B 的现代科学记录…”）。裁判模型通过提取生成文本中的转折关系词和最终结论，比对 Ground Truth（标准答案）。如果结论选错了，或者把对错混为一谈，该项即为 Fail。
  1. Function Call 能力评估
  • 测试目的：评估系统何时该用知识库，何时该调用外部 API。
  • 如何构造测试（挖坑）： 混合输入两类问题。第一类是静态问题（如“RAG 的原理是什么”），第二类是动态问题（如“帮我查一下今天上证指数的收盘价”）。
  • 评估原理与打分机制： 这就回到了你前一张图中的公式链路。系统不看生成的文本，而是直接拦截 Agent 输出的 JSON 数据流。
    • 如果遇到动态问题，系统没有输出调用 get_stock_price API 的 JSON，则记为意图识别失败。
    • 如果提取的股票代码参数错误，记为参数识别失败。
    • 这是一种高度确定性的白盒评估，基于预设的 Schema 字段进行严格的 Exact Match（精确匹配）打分。
  1. 时效性评估

  • 测试目的：确保模型能够识别出时间戳的先后顺序，并优先采信最新数据；同时测试系统的上下文组装策略是否合理。

  • 如何构造测试（挖坑）： 针对频繁变动的实体提问（如“现任 OpenAI CEO 是谁？”）。注入多篇带有不同日期的文档（比如 2022 年、2023 年 11 月 18 日、2023 年 11 月 21 日的不同报道）。

  • 评估原理与打分机制： 这里分为两个层面的评估：

    • 系统工程层评估：检查 Prompt 构建器是否利用了图中所说的“注意力特点”。大语言模型存在 Lost in the middle（遗忘中间） 现象，对开头和结尾的文本注意力最强。评估脚本会检查系统是否成功将日期最新的文档排序到了 Prompt 的最头部或最尾部。
    • 模型生成层评估：提取最终答案中的时间节点和结论，与最新的 Ground Truth 进行绝对时间戳对比。如果模型回答了旧信息，得分为 0。
  1. 拒答评估
  • 测试目的：测试模型对自身知识边界的认知（“知之为知之，不知为不知”），这是核心的安全兜底策略。
  • 如何构造测试（挖坑）： 输入一个极度生僻、或者完全虚构的问题（例如“解释一下马斯克在火星上建立的‘火星第一人民医院’的运作机制”）。检索器自然会返回空结果，或者返回完全无关的火星百科。
  • 评估原理与打分机制：
    • 全部拒答 评估：强制匹配生成的回答中是否包含预设的拒答模板（如“抱歉，根据提供的文档，我无法回答…”）。如果模型依然一本正经地胡说八道（产生幻觉），该项安全得分直接清零。
    • 部分拒答评估：提问包含已知和未知两部分（如“解释马斯克创立的 SpaceX，以及火星第一人民医院”）。评估模型是否能精准剥离信息：“关于 SpaceX 的信息如下：…但关于火星医院，文档中未提供信息。” 裁判模型需要通过语义分割，分别评估回答的“命中部分”和“拒答部分”是否准确对应了事实库的边界。

开源RAG评估框架

当我们将前面的理论指标（如召回率、事实性）落地到具体的工程实践时，必然需要借助标准化的测试工具。 Ragas 和 LangSmith，正是目前业界最主流的两大开源基础设施，但它们的定位截然不同：Ragas 是一个“自动化打分器（打分框架）”，而 LangSmith 是一个“透视诊断台（可观测性平台）”。

一、 Ragas：基于 LLM-as-a-Judge 的无参考评估框架

传统的自然语言评估（如 BLEU）严重依赖人工提前写好标准答案，这在多变的 RAG 问答中成本极高。Ragas 的核心原理是完全抛弃标准答案，利用一个强大的大语言模型（如 GPT-4）作为裁判，直接基于“用户问题 (Query)”、“检索出的上下文 ”和“系统生成的答案”这三元组进行闭环打分。

它主要通过极其严密的 Prompt 链条，量化计算图中的三个核心指标：

  1. 忠实性 —— 评估“生成器 ”是否产生幻觉
  • 评估原理：生成的答案必须完全能从检索到的上下文中推导出来。
  • 具体过程（逆向拆解法）：
    1. 陈述提取：Ragas 首先让 LLM 裁判阅读生成的 Answer，并将其强行拆解为一组独立的、原子化的陈述句集合。
    2. 证据校验：针对每一个陈述句，裁判模型去检查 Context，判断该陈述是否被 Context 所支持（蕴含关系）。
    3. 量化打分：$忠实度分数 = \frac{被上下文支持的陈述数量}{提取出的总陈述数量}$。如果分数为 1.0，说明答案 100% 来源于参考资料，毫无幻觉。
  1. 答案相关性 —— 评估“生成器 ”是否答非所问
  • 评估原理：一个高相关的答案，应该能让人一眼看出来它在回答什么问题。它不评估答案的对错，只评估答案是否聚焦于原始提问。
  • 具体过程（逆向提问法）：
    1. 逆向生成问题：Ragas 故意隐藏用户的原始 Query，只把生成的 Answer 交给裁判模型，要求裁判根据这个答案，反向生成 $N$ 个可能的原始问题。
    2. 向量相似度计算：将裁判反向生成的 $N$ 个问题，与用户真正的 Query 进行 Embedding 向量化，并计算它们之间的余弦相似度。
    3. 量化打分：取这些相似度的平均值。如果答案充满了废话，裁判反推出来的问题必然会偏离原意，导致最终的相似度得分极低。
  1. 上下文相关性 —— 评估“检索器 ”的纯度
  • 评估原理：正如图片中所述，大模型处理长文本不仅成本高昂，且极易出现“Lost in the middle（遗忘中间）”现象。因此，检索回来的 Context 必须是高度浓缩的精华，不能夹杂废话。
  • 具体过程（信息抽取法）：
    1. 关键句提取：给定用户的 Query 和检索出的完整 Context，要求裁判模型从 Context 中逐句挑选出“必须依赖这句话才能回答用户问题”的核心句子。
    2. 量化打分：$上下文相关性分数 = \frac{提取出的核心句子数量}{Context 中的总句子数量}$。分数越低，说明检索器塞入的无效噪音越多。

二、 LangSmith：全链路的可观测性与调试平台

如果说 Ragas 告诉你“系统考了 60 分”，那么 LangSmith 就是用来查明“这扣掉的 40 分到底错在哪个微小的执行步骤里”。它是一个面向大模型应用层的 APM（应用性能监控）平台。

  1. 评估原理：白盒化的执行追踪

由于现代 AI 系统往往不是单一的 LLM 调用，而是复杂的架构。例如，在构建具有感知、规划和执行架构的复杂 Agent 时，整个运作过程是一个隐式的黑盒。LangSmith 的原理是通过在代码底层进行“埋点”，将每一次数据流转都记录为树状的 Trace（追踪）和 Span（跨度）。

  1. 具体过程：从调试到监控
  • 可视化微观步骤：当输入一个问题时，LangSmith 能够将隐藏在模型内部的思维链调用、Prompt 模板的实时拼接结果、以及每一次 Function Call 的输入输出参数完全可视化。开发者可以直接看到模型在某一步推理时，是不是由于某个中间 Prompt 没写好而导致了逻辑断裂。
  • 构建回归测试集：在 LangSmith 中，你可以随时将生产环境中表现不佳的对话一键保存为一个测试数据集。当你修改了系统架构（比如优化了某个双指针检索算法或调整了 Chunking 策略）后，可以在这个数据集上批量重跑，验证修改是否有效。
  • 无缝集成自动化打分：LangSmith 本身不自带复杂的打分逻辑，但它的架构设计可以直接将前文提到的 Ragas 打分脚本以内置评估器的形式挂载上去。使得每一次代码迭代，都能自动生成一份详尽的多维度诊断报告。
